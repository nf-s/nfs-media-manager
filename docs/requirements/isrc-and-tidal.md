# ISRC and TIDAL matching

TIDAL is added as a catalogue, matching and related-music source. Spotify stays the only player: nothing plays through TIDAL, whose third-party playback is limited to 30-second previews. The build has three stages, each released through `main` on its own:

1. ISRC recovery and ISRC as an identifier.
2. A TIDAL provider that matches albums by UPC and tracks by ISRC.
3. Similar albums and tracks from TIDAL, mapped back to Spotify for playback.

## Stage 1: ISRC as an identifier

- ISRC-01: An ISRC is a provider reference on the library track: a `provider_reference` row with `reference_type` `isrc`, `provider` set to the service that reported it (`spotify` now, `tidal` from stage 2) and `external_id` set to the normalised code: 12 characters, uppercase, hyphens and spaces removed. A value that is not a valid ISRC is not stored. `metadata` records where the code was read: the kind of source (playlist import, track search, album job, legacy import), the snapshot, response or job it came from, and when.
- ISRC-02: A track can hold several ISRCs, and one ISRC can sit on several library tracks (the same recording on an album, a compilation and a playlist). Lookup by ISRC uses the existing `(reference_type, external_id)` index on `provider_reference`.
- ISRC-03: `library_track.isrc` stays the primary ISRC that recording groups, track search and the Tracks API read. Recovery fills it only when it is empty, with the ISRC of the track's own Spotify track object. It never replaces a stored value. Where references disagree with the primary value, every code stays stored and is listed in the track's details.
- ISRC-04: Recovery reads only data already stored: the ISRC already on a library track, Spotify track and search responses stored by artist enrichment and track search, the candidates saved by track search jobs, and the raw legacy playlist files stored as snapshots (ISRC-06). A track object is matched to a library track by Spotify track ID only, so a search candidate gives its ISRC to the library track with that Spotify ID, never to the track it was searched for. Album payloads hold only simplified track objects without ISRCs, and playlist imports write the ISRC directly. Running recovery again changes nothing. A playlist import never replaces a stored ISRC with an empty one, and each import, track search and manual addition records its ISRC as a reference too.
- ISRC-05: Album UPCs found in stored Spotify album payloads but missing from the album's references are recorded the same way, as `spotify` `upc` references. (On 2026-11-22 every stored album UPC was already a reference.)
- ISRC-06: The legacy Spotify responses are present in the app. Legacy Spotify responses that are on disk but not in the database are imported as provider snapshots attributed to the legacy import, through the existing legacy import path, which reuses an identical earlier snapshot. Every legacy album response was already a snapshot. The raw Spotify playlist files (`*-raw.json`, full track objects with ISRCs) were not read by the import: each is now stored once as a media-less `spotify` snapshot with source `legacy-import:<file>`, without audio features, and an identical file is not stored again. The result of the search, the import and what remains missing is reported to the owner.
- ISRC-07: Recovery writes in bounded batches so that each statement stays small for the Browse cache and duplicate-group triggers. A run in a scheduled Worker invocation issues tens of statements, not thousands.
- ISRC-08: Track details list every ISRC with the service it came from. The Spotify track search review in Tracks → Matches shows the library track's ISRC above the candidates' ISRCs. Both use existing components.
- ISRC-09: Tracks with a Spotify ID and no ISRC after recovery, nearly all from album track lists, need new Spotify requests. Spotify's batch track endpoint (`GET /v1/tracks?ids=`, up to 50 IDs) still answered for this app on 2026-11-22, so this is one request per 50 tracks. That fetch is a Spotify job that stores its responses, and it is not started until the owner agrees to the request count and rate.

Why a provider reference and not a column or a new table: a single column cannot hold several codes or say where each came from. `provider_reference` already gives a per-provider source, a unique key per item, provider, type and value, an index for lookup by value and removal with the media item, and album UPCs already use it. A dedicated table would duplicate those.

## Stage 2: TIDAL provider

The owner agreed on 2026-11-22 to start this stage beside stage 1, with a live test on albums and some tracks first.

Live test (2026-11-22, country AU, about 40 requests 2.5 seconds apart, library items chosen read-only):

- Albums by UPC: 11 of 13 found, each with one album whose barcode equals the stored Spotify UPC as stored (12, 13 and 14 digits). The two misses were large Japanese compilations that TIDAL does not have in AU, US or JP; a miss is an empty `data` list with HTTP 200. Track counts equalled the library's on every hit. One request returns the album and its first 20 tracks with their ISRCs; longer albums page by a cursor on the album's `items` relationship (20 a page).
- Tracks by ISRC: 20 of 20 found. 9 returned two to four TIDAL tracks: the same recording on a single, an EP, the album and compilations, nearly always with the same duration and version. The library album's UPC settled all but one of those with a UPC; there, two TIDAL albums shared the barcode and only one track was streamable. One track had no library album UPC and four identical candidates.
- One request accepts up to 20 barcodes or 20 ISRCs (one result each). No rate-limit headers were sent and no request was refused.
- TIDAL returned no BPM, key or key scale for any track, including single-track requests, although its specification lists them. The stage 3 probe saw none on 126 tracks either.

- TIDAL-01: A built-in provider `tidal` for albums and tracks. It uses the client-credentials grant; the token is cached until shortly before it expires and never reaches the browser. The client ID and secret are provider secrets (`TIDAL_CLIENT_ID`, `TIDAL_CLIENT_SECRET`); an optional country (default `AU`) sets the catalogue it answers for.
- TIDAL-02: Requests go through the project's request gate with a concurrency of one and 1.5 seconds between starts. A 429 starts a cooldown from its `Retry-After` header, or five minutes without one. Every request and response is stored like every other provider's, and every payload is validated with a schema before use.
- TIDAL-03: Albums match by the UPC of their Spotify album with `filter[barcodeId]`, or by a TIDAL album ID already stored for them, never by a text search. A match stores the TIDAL album ID and link as a `tidal` reference. The album's TIDAL tracks are then aligned to the library album's tracks by position, duration and title. An aligned track gains a `tidal` `track` reference holding its TIDAL track ID, link, version, duration and popularity, and BPM and key when TIDAL returns them; its ISRC as a `tidal` `isrc` reference; and its ISRC as the primary ISRC when it had none and the alignment agreed on duration. One request covers an album of up to 20 tracks.
- TIDAL-04: Tracks match by ISRC with `filter[isrc]`. When several TIDAL tracks share the ISRC, the choice uses the album UPC, then duration, then version, then whether the track can be streamed. A track that is still ambiguous is offered for review in Tracks → Matches and its Sources instead of being guessed. A matched track gains the same `tidal` `track` and `isrc` references.
- TIDAL-05: A job is one provider and one media item. Metadata selection shows TIDAL freshness like the other providers. A bulk run is started by the owner and checked on one item first. Album jobs come first: they supply ISRCs for most album tracks that have none, so a track job is needed only for tracks with an ISRC that are not on a matched album.

## Stage 3: Similar albums and tracks

The owner asked for this stage on 2026-11-22 ("give it a go"); the interface is concept A (SIMILAR-04).

- SIMILAR-01: For a matched album, TIDAL `similarAlbums`; for a matched track, `similarTracks`. Each is one request for the first page of 20, with `include=similarAlbums,similarAlbums.artists` or `include=similarTracks,similarTracks.artists` so that titles, artists, version and the ISRC or barcode arrive in the same response. Both answer with the client-credentials token; no TIDAL sign-in is needed. `radio` and `suggestedTracks` are not used: in the probe on 2026-11-22, a track's radio was a playlist, needing a second request, whose items were the track itself followed by its `similarTracks` in the same order; `suggestedTracks` returned nothing for every track. The response is stored with the job like every other provider response, and the suggestions are kept in `tidal_similar`, one row per library album or track they were read for, not as library items; the next read replaces them. They are read by a TIDAL task job (`tidal-similar`) for that one item, never while the page loads: opening the Similar tab of a matched item that has never been read queues the job. An empty list is a result too: in the probe, a small EP had no similar albums. Suggestions carry no BPM or key. They keep TIDAL's order and include the item's own artist when TIDAL does, 2 to 4 of 20 in the probe.
- SIMILAR-02: Each suggestion is mapped for playback through Spotify. A suggestion is in the library when a track's ISRC is an `isrc` reference of a library track, or an album's barcode, leading zeros ignored (TIDAL and Spotify write barcodes with different numbers of leading zeros), is a `upc` reference of a library album. This is worked out each time the tab is read, so items added to the library later count. For the rest, the TIDAL job queues one Spotify task job (`spotify-similar-lookup`) for the same item, because a job's requests and responses belong to one provider: a Spotify `isrc:` or `upc:` search through the Spotify request gate, one request per suggestion, at most 20 per item, never library-wide. A UPC is searched as TIDAL wrote it. Every tested suggestion was found: 6 of 6 tracks and 4 of 4 albums. An `isrc:` search can return several Spotify tracks for one recording, up to 8 in the probe: the single, the album and compilations. The choice is a Spotify track that is already a library track, then the earliest release that is not a compilation, then Spotify's first. (A step choosing the Spotify track on the album whose UPC matches the TIDAL track's album was dropped: `similarTracks` with artists included carries no albums, and Spotify search results carry no UPC.) A Spotify ID found that belongs to a library item counts as in the library. The Spotify ID found, or the miss, is stored in `spotify_code_lookup` by code with the time of the search as soon as it is found, reused for every item that suggests the same code, and a miss is searched again only after 30 days. A suggestion is shown as in the library, on Spotify only, with no Spotify match, or not looked up on Spotify when Spotify could not search (no market and no connected account, or a cooldown). Since SONO-26 ([Sonovault](sonovault.md)), similar tracks are first sent by ISRC through one Sonovault bulk request (`sonovault-similar-lookup`); a verified match is stored in `spotify_code_lookup` with `source` `sonovault`, and only the ISRCs it does not map, or all of them when Sonovault cannot be used, go to the Spotify search above. Similar albums are searched on Spotify by UPC as before.
- SIMILAR-03: A suggestion in the library opens it. One on Spotify only can be played or queued with the existing play controls and opened on Spotify. One with no Spotify match links to its TIDAL page and has no play control. Nothing starts playing unless the owner presses play. An item not yet matched on TIDAL says so and offers the TIDAL match job (an album job by its Spotify UPC, or a track match by its ISRC). While a match, read or Spotify lookup is queued or running, the Similar area says so. A list that came back empty says that TIDAL has no similar items.
- SIMILAR-04: The interface is concept A, accepted by the owner on 2026-11-22: a Similar tab after Overview in the album and track drawers, one list row per suggestion, its second line starting with In library, On Spotify, Not on Spotify or Not looked up on Spotify. It is in the design system as the Similar section of the components page (`SuggestionRow` in `packages/ui/src/components/ds/suggestion.tsx`); the concept page is deleted.

## Not in scope

TIDAL account sign-in, TIDAL playlists and TIDAL playback. A later stage that needs the owner's TIDAL account uses the callback route `/api/v1/tidal/callback`, which is registered with TIDAL.
