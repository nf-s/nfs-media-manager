# Device store

A device keeps a copy of the library in SQLite and answers Browse reads from it. PostgreSQL stays the source of truth. The server publishes finished rows and a numbered change feed; shared TypeScript exposes the same read operations from the API or from SQLite. Three stages: the server feed (DEVICE-01 to 12), the store package (DEVICE-20 to 33) and the web client (DEVICE-40 to 47).

Out of scope: a desktop shell, a phone app, offline playback, an offline queue for edits and artwork caching.

## Contract between the stages

The contract is `packages/schemas/src/device.ts` (row shapes, feed requests and responses) and `packages/library-source/src/source.ts` and `driver.ts` (the two interfaces). A change to any of them changes this page in the same commit.

### Entities

| Entity             | Key                  | Holds                                                                                                                                             |
| ------------------ | -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `track`            | media item ID        | `TrackListItem` and its projection                                                                                                                |
| `album`            | media item ID        | `AlbumListItem` and its projection                                                                                                                |
| `film`             | media item ID        | `FilmListItem` and its projection                                                                                                                 |
| `artist`           | artist ID            | `ArtistSummary` without `listeningScrobbles`, `listeningMonths` and `links`, and its projection                                                   |
| `playlist`         | playlist ID          | `PlaylistSummary` without `sync.job`, with `sync.nextScheduledAt` as it is with no job, and its projection                                        |
| `playlist_job`     | sync group key       | the latest Spotify import job of the group (`SpotifyPlaylistJob`)                                                                                 |
| `tag`              | tag ID               | name, key, library, kind, hidden, alias target, identity keys, and whether some library track holds it in Browse from Sonovault, published or not |
| `tag_key`          | `<library>:<key>`    | the ancestor keys of one normalised name, from `tag_ancestor`; a key without ancestors has no row                                                 |
| `scrobble_name`    | hash of the name key | play times of one scrobbled name (listener, artist key, track key), as epoch seconds                                                              |
| `album_plays`      | album ID             | play times of scrobbles linked to the album                                                                                                       |
| `artist_plays`     | artist ID            | play times of scrobbles attributed to the artist, each scrobble once                                                                              |
| `meta`             | name                 | `fields:album`, `fields:film`, `fields:track`, `fields:artist`, `listening` (start date), `providers` (names), `fold` (the database's `lower()`)  |
| `library_playlist` | library playlist ID  | the Playlists directory's row of a library playlist and its `LibraryPlaylistSummary`, and its projection, for every library                       |

The `fold` row is `{ kind: 'fold', codePoints, lower }`: every code point `c` from 1 to U+10FFFF outside the surrogates for which `lower(chr(c))` differs from `chr(c)` in the server's database, in ascending order, and at the same index the result as a string (a database whose `lower()` yields several characters is represented as it is). One statement computes it, without reading a table: about 1,500 code points and 14 kB of JSON, and 0.2 to 0.4 s of one CPU, once per sweep. The device folds text with this mapping and nothing else, since its engine's Unicode version may differ from the database's.

The tag hierarchy lives only in `tag_key`: a re-parent changes `tag_key` rows and no item row. A key is hidden when any tag with that key is hidden. The device sets a playlist's `sync.job` from its `playlist_job` row, and `sync.nextScheduledAt` to null when that job has not succeeded. A queued or running job's row carries its status without progress, so progress writes do not change the feed; a page that holds a playlist with such a job falls through to the API, which has the progress.

Only rows in the default scope are published: in the library, not merged away, and for tracks, albums and films including archived rows with a flag (Albums and Films can show them). A row leaves the feed as a tombstone when it is deleted, merged away or removed from the library. Library playlists of all five libraries are published while they are not deleted; a deleted one, restorable or purged, is a tombstone.

### Row shape

Every item row (`track`, `album`, `film`, `artist`, `playlist`, `library_playlist`) is `{ item, text, search, num, sort, extra }`:

- `item`: the list item exactly as the API returns it for an unfiltered request, without request-dependent fields (`listeningScrobbles`, `recordingGroup`, `links`).
- `text`: for each text field matched by value, the raw values a filter on that field compares with, distinct, as the Browse service reads them. Tag fields are matched through `extra`.
- `search`: for each field that `q` searches, the values a word may match, where they differ from `text` or `text` has none.
- `num`: for each range field, the number the range compares with; dates as whole epoch microseconds, the stored precision. A range bound arrives in milliseconds and is multiplied by 1000.
- `sort`: for each sort key, the value the service orders by where it is not the `num` value, already lower-cased by PostgreSQL; the Tags sort at each location (Auto and every `tagLevels` combination); for Tracks the natural-order values.
- `extra`: per entity. Tracks: archived flag, redundant Last.fm placeholder flag, linked album ID, credited artist IDs, `has_own_tags`, tag IDs per level (own, own from Sonovault, album), album release-tag count, raw artist tag keys, projected artist tag keys, library-wide recording group key and the representative ordering values, scrobbled name IDs. Albums: archived flag, edition flag, credited artist IDs, release tag IDs, release-tag count, raw and projected artist tag keys, own tag IDs of the album's library tracks. Films: archived flag, source kind, tag IDs, credited person IDs by role. Artists: raw tag keys, playlist IDs. Playlists: source, sync group key. Library playlists: library, type, whether it has a view, and the distinct items of its listed entries (media item IDs, or subscription item IDs for Subscriptions and Mixes) in ascending order.
- Library playlists: `item` is `librarySummary` (`playlist-directory.ts`) as a directory read with `library` and no count range gives it (`itemCount` is the listed entries of a playlist and null for a smart playlist), and `summary` is the playlist list's summary without `containsItem`; `text` is empty, `search.name` and `sort.name` are the name and its lower case, `num.count` is the listed entries (null for a smart playlist), `num.updated` and `num.added` the playlist's times.
- Playlists without `library` (importedSortColumn, `playlist-directory.ts`): the `type` and `count` sorts have the same value on every row (Playlist, and no count), so in either direction they order by the ascending name and ID tie-break, and `updated` orders by `num.imported`.
- Albums and Films: `text`, `num` and `sort` also hold every other key of `metadata.browse`, so a plugin field is read from the row. A field missing from the device's `fields:<library>` row falls through.

The server fills `text`, `search`, `num`, `sort` and `extra` with the same SQL expressions the Browse service filters, searches and orders by, so the two cannot drift. The device never recomputes them. Each field in `device.ts` names its expression.

### `LibrarySource`

One method per read. Each returns `{ served: true, data }` or `{ served: false, reason }`; a source never returns a partial or approximate answer.

- Tracks: `trackPage`, `trackCount`, `trackList`, `trackPositions`, `trackRecordings`, `trackFacets`, `trackHistogram`
- Albums: `albumPage`, `albumCount`, `albumList`, `albumFacets`, `albumHistogram`
- Films: `filmPage`, `filmCount`, `filmList`, `filmFacets`
- Artists: `artistPage`, `artistCount`, `artistFacets`, `artistHistogram`
- Playlists: `playlistPage`, `playlistCount`
- `fields(library)`

Arguments and results are the existing shared schemas, parsed (`TrackQuerySchema`, `TrackPositionsQuerySchema`, the histogram query schemas, `AlbumQuerySchema`, `FilmQuerySchema`, `ArtistQuerySchema`, `PlaylistBrowseQuerySchema`, `BrowseFacetQuerySchema`, `ArchivableBrowseFacetQuerySchema`, the page, count, facet and histogram schemas); `source.ts` lists them per method. `trackRecordings` takes the track ID with its query. `artistFacets` answers in the shape the route uses, `FilmFilterOptionSchema`. `playlistCount` has no `unfilteredCount`. `resolveLibraryRead(method, path)` maps an API request to a `LibraryRead` (a method and its parsed query), or to nothing. Implementations: `RemoteLibrarySource` (the API), `DeviceLibrarySource` (SQLite) and `FallbackLibrarySource` (device first, then remote).

### `SqliteDriver`

```ts
type SqlValue = string | number | null
interface SqliteExecutor {
  run(sql: string, params?: readonly SqlValue[]): Promise<void>
  all(
    sql: string,
    params?: readonly SqlValue[],
  ): Promise<Record<string, SqlValue>[]>
}
interface SqliteDriver extends SqliteExecutor {
  /** Several statements without parameters, for the schema. */
  exec(sql: string): Promise<void>
  /** Runs `work` in one transaction; rolls back when it throws. */
  transaction<T>(work: (tx: SqliteExecutor) => Promise<T>): Promise<T>
  close(): Promise<void>
}
```

The store uses nothing else from a host: no custom SQL functions, collations or extensions beyond FTS5 with the trigram tokenizer. Case folding and normalisation happen in TypeScript before a value is stored or bound. The fold is the `fold` row's mapping, code point by code point (no context rules such as a final sigma); a lone surrogate in a query value folds to U+FFFD, as the server's UTF-8 encoding sends it. Where a service lower-cases a value in TypeScript (`toLowerCase`, `normalizeTagName`), the device computes what the server's engine gives from the same mapping, and falls through with `server-lower-case` where the mapping cannot settle it (see Known holes): settled are ASCII, U+0130 (ECMAScript adds a combining dot), a code point the database changes to one code point (the server's engine is assumed to know at least its database's Unicode version), and the lower-case letters the mapping yields and U+03C2, which do not change. Tag keys come from the rows, never from a TypeScript normalisation of stored names. Code-point order means comparing UTF-8 bytes or code points, not UTF-16 units.

## Stage 1: server feed

- DEVICE-01: `device_row(entity, id, payload, hash, seq, deleted, rendered_at)` holds one row per published item. `seq` comes from one sequence. All writes to `device_row` run under one transaction-level advisory lock, so rows commit in `seq` order and a reader never misses a lower number.
- DEVICE-02: Rows are rendered by the code that builds the API list items (`loadTracks`, `loadAlbums`, `loadFilms`, `loadArtists`, `loadPlaylistSummaries`) and by projections assembled from the Browse service's own SQL expressions. `hash` covers the payload in a canonical key order. A row whose hash is unchanged keeps its `seq`.
- DEVICE-03: Statement-level triggers on every contributing table insert `(entity, id)` into `device_dirty`, following the `mark_browse_cache_dirty()` pattern and running statements that join transition tables through `EXECUTE`. A change that affects many rows (tag hidden, merged or re-parented, artist renamed, playlist or album renamed) marks the rows that hold it. A track tag held in Browse from Sonovault that appears, disappears or changes marks its tag, on any library track, published or not. A change that decides whether another row is published or what it shows marks that row too: an item entering or leaving the library marks its scrobbled names and album plays; an album row, an added or observed artist, and the artist it is merged into mark the artist plays in scope; a member that may be the last to make a playlist without a source visible marks the artists of every member. A delete marks the deleted ID. A library playlist is marked by writes to it and to its entries, including entries deleted by a cascade from their media item, subscription item or playlist; an entry's position, addition batch and times are not compared.
- DEVICE-04: A render task takes dirty marks in bounded batches, renders them, writes changed rows and tombstones, and deletes only the marks it read. A track mark also re-renders the visible tracks that share its title key and the tracks published with the same recording key (`extra.recording.key` in the stored rows, read before the batch writes), because recording groups depend on them; a title change, archive or delete therefore updates the rest of the old group without a sweep. It also re-renders the Last.fm placeholders whose names are linked exactly to the track, because `extra.redundantPlaceholder` depends on whether such a track can play. When a render throws an error other than a database error, the batch's IDs are halved until each failing ID is alone. A row isolated alone is set aside: the other rows of the batch are written, its stored row stays as it is, its mark is consumed, the next sweep renders it again, and the maintenance event and the request log count set-aside rows by entity without IDs or content. A failing part of several rows that fails after the time budget has passed is neither written nor counted: its rows are marked again behind the marks already queued, so the marks after it render first, and a later run with time to split it (maintenance renders for 15 seconds) sets aside only the failing row. A mark is therefore consumed only when its row was written, found unchanged, tombstoned or set aside alone. It runs in the five-minute maintenance task and before `changes` answers, within a time budget of 2 seconds: there the first batch reads 20 marks and each later one as many as the time per mark so far fits in the time left (at most twice the last and 200), so a call that finds marks renders some and answers about one small batch past the budget. A restart for a new row version removes the marks made before it, which the sweep that follows covers.
- DEVICE-05: A sweep re-renders every entity in ID order, a bounded number of rows per run, and writes only rows whose hash differs or that no longer exist. IDs are listed, compared and ordered in SQL in the database's default collation, the collation of `device_row.id`, so each source table's key index serves a page; no code compares IDs by order outside SQL, and devices need no ID order because they page by `seq`. A listing may include IDs that render nothing (Artist plays list every artist in scope); those are written as absent. The first sweep builds the feed and runs in every maintenance run until it completes; until then the feed reports `ready: false`. A restart for a new row version does the same. `device_feed_state.built_entities` counts the entities, in `DeviceEntitySchema` order, that the last completed sweep covered, and a completed sweep sets it to the list's length. While it is lower, because a release added an entity without changing the row version, the feed reports `ready: false` and a sweep is due: on a built feed the sweep cursor moves to the first entity not covered, abandoning a routine sweep in progress (the next starts after the rest), and a first build continues where it is, since new entities come last. No row already in the feed is rendered again for it, and `snapshot` and `changes` answer as before. A server without the entity drops its marks. After a sweep completes, the next one starts no sooner than 24 hours later (`SWEEP_REST_HOURS`) and, once started, continues in every run until it completes, so a missed trigger is corrected within about a day. The dirty-mark render runs in every maintenance run; a run with no marks, no sweep due and no tombstones to prune is one statement.
- DEVICE-06: `GET /api/v1/device/state` returns `{ ready, epoch, seq, minSeq, rowVersion }`. `ready` says the feed is built, of this row version and covers every entity (DEVICE-05). `epoch` changes when the feed is rebuilt from nothing, `rowVersion` when the row shape changes, `minSeq` is the oldest sequence from which tombstones are still held.
- DEVICE-07: `GET /api/v1/device/snapshot?epoch=&entity=&after=&limit=` returns live rows of one entity in `seq` order, without tombstones, with `{ rows, seq, hasMore }`. `GET /api/v1/device/changes?epoch=&since=&limit=` returns rows and tombstones of every entity in `seq` order with `{ rows, seq, hasMore, pending }`; `pending` says dirty marks remain. Another `epoch` on either route, or a `since` below `minSeq`, answers `{ reset: true }`, judged by the state read in the same statement as the page, so a restart or a prune during the request also answers `{ reset: true }`. Pages are bounded by row count and by payload bytes.
- DEVICE-08: A device applies a snapshot by reading the state, paging every entity, then reading changes from the sequence in that first state. Rows are upserts keyed by `(entity, id)`, so a row seen twice is harmless.
- DEVICE-09: Tombstones are kept for 90 days. Spotify-sourced values in a row are a cache: they are replaced by sync and never the only copy.
- DEVICE-10: Device sign-in follows local-worker pairing. A signed-in owner creates a one-time pairing code; a device exchanges it for a device token; the server stores only hashes. The token is an API key of kind `device`, sent as `Authorization: Bearer`: it has an API key's access and no more, is listed and revoked with the other keys, and reads the device routes. Routes that accept it answer CORS preflights for the origins in `DEVICE_ALLOWED_ORIGINS` (none by default) without credentials.
- DEVICE-11: Routes are thin, with request and response schemas in `packages/schemas/src/device.ts`. The feed adds no statement to any existing request.
- DEVICE-12: The performance suite budgets a render batch (statements and shared blocks per 100 rows of each entity), a sweep batch of each entity (its listing, and the listing with the render of 500 IDs), a `changes` page, a maintenance run with nothing to do and one rendering 200 marks, and the trigger cost of a single-row and a bulk write on each trigger table, library playlists and their entries included.

Check on a disposable database with the synthetic library (`device-feed-end-to-end.integration.ts`): after building the feed, each edit (item, artist and tag edits, tag visibility, aliases and parents, item tags, artist and album merges, playlist members and names, an import job's progress, new scrobbles, archive, restore and delete, a recording group member's title change, archive and delete, a Sonovault tag added to, unverified on and deleted from a track outside the library, and a library playlist created, renamed, deleted and restored, with entries added and removed, an addition undone, a removal restored and a held item deleted), made through the service or route where one exists, appears in `changes` as exactly the rows whose payload differs, each equal to a fresh render (a library playlist's also to the directory's row and the list's summary), and a sweep after each writes nothing. A feed built before library playlists builds them, reporting `ready: false` until then, without renumbering a row, whether it is ready with no sweep, ready with a routine sweep in progress or in its first build.

## Stage 2: store package

- DEVICE-20: `packages/library-source` holds the interfaces, the three sources, the sync client, the SQLite schema, the query compiler and the drivers. It depends on `@repo/schemas` only.
- DEVICE-21: SQLite schema: one table per item entity with the payload and indexed columns for archived and the common sorts; `item_text(entity, id, field, value, folded)`, `item_search(entity, id, field, folded)` with an FTS5 trigram index, `item_num(entity, id, field, value)`, `item_sort`; `item_tag(entity, id, level, tag_id)`, `item_artist_tag_key`, `item_credit`; `tag`, `tag_identity`, `tag_ancestor`; `name_play`, `track_name`, `album_play`, `artist_play`; `sync_state`, with a `generation` that every schema build renews. A schema version change, or a sync state row that is missing or does not parse, drops the store; the next sync fills it as a first fill.
- DEVICE-22: The compiler turns a parsed query into SQL with the service's semantics: filter modes (required ANDed, exclude negated, any and unset in one OR group across fields), case-insensitive equality on folded values, `q` as words that each match some searched field, inclusive ranges with `includeMissing`, the tag filter (the tag, its aliases, its visible descendants; levels and Auto; the artist-tag fallback for albums with fewer than two release tags), the redundant-placeholder rule, creator scope, `limitResults`, archived and edition toggles, `unfilteredCount`, and sorting as primary value, nulls last (except `title desc`), the natural order and the ID.
- DEVICE-23: Listening rules, listening sort and histograms are computed from play times with the service's period arithmetic (UTC calendar months, exclusive end for date periods, "now" taken once per call). Track counts go through scrobbled names; a recording group counts each name once.
- DEVICE-24: Grouped Tracks: matching rows are grouped by the server's recording group key; version count, representative row, group dates and group scrobbles are computed over the matching rows as the service does.
- DEVICE-25: Facets: counts over the whole library in scope, word matching, exact match first, count, then value; tag values counted under each visible ancestor, with `subtags`; the per-field limit rule of each library. Where the API orders facet values in application code, the server and the device call one comparator exported from `packages/schemas`, with its locale named, so equal counts fall in the same order on both.
- DEVICE-26: Text is folded with the server's `fold` row and nothing of the device's engine, and ordered by code point on folded values, matching a PostgreSQL database with the `C.UTF-8` collation. An installation with a language collation orders punctuation, case and accents differently on the device; this is a stated limitation. So is a database whose `lower()` applies context rules (a final sigma), which the per-code-point mapping does not represent.
- DEVICE-27: The compiler decides support before running anything. A query it does not fully support returns `{ served: false, reason }`. See Known holes. The store holds no library playlists (PL-17, PL-18): a Browse read whose filters hold `libraryPlaylist` in any mode (pages, counts, lists, positions, recordings and histograms of Tracks, Albums and Films) and a Playlists directory read with `library` (page and count) answer `library-playlist`. Reasons are checked in the order of reasons under the Known holes. Without `library`, the Playlists sorts `type` and `count` order by the name and ID tie-break and `updated` by `num.imported`, as the service orders imported playlists. A store answers only when its fill has completed for this package's `DEVICE_ROW_VERSION` and SQLite schema version and it holds the `fold` row; any other store is `not-ready`. A store or driver failure during a read answers `store-error`.
- DEVICE-28: The sync client applies each snapshot page and each change page in one transaction, including the derived tables and the cursor, so a reader sees the previous complete state or the next. It handles `reset`, a changed `epoch` or `rowVersion` by refilling, and reports progress. A fill pages `meta` first, so the `fold` row is stored before any item row; an item row while the store has no `fold` row fails the page and leaves the store not ready. A change page whose `fold` row differs from the stored one refills the store from nothing, since the stored folded values are stale.
- DEVICE-29: Drivers: `better-sqlite3` for Node and tests, `@sqlite.org/sqlite-wasm` on OPFS (`opfs-sahpool`) for a browser Worker. A driver is the only host-specific code.
- DEVICE-30: `clear()` removes every row and the cursor. Sign-out calls it. It renews the store's `generation`; a running sync checks the generation inside each page's transaction, so after a clear from any connection it writes nothing more, never marks the store ready, and ends with `{ status: 'cleared' }`. A sync asked for while a cleared one is ending runs afresh.
- DEVICE-31: The store holds no credentials.
- DEVICE-32: Parity suite (`apps/server/integration/device-parity.integration.ts`, its helpers in `integration/device-parity/` and its library in `integration/fixtures/device-parity-library.ts`). On a disposable PostgreSQL database ordered by code point (the builtin `C.UTF-8` locale, else libc `C.UTF-8`, else the `C` collation), seeded with a synthetic library, the real maintenance sweep builds the feed, `syncStore` fills a `better-sqlite3` store through the feed routes, and for every path of a generated matrix the route's answer (through the app, so query parsing is included) is compared with the device's answer for the same path (`resolveLibraryRead`, then the source). Both are parsed with `libraryResponseSchemas` and must be equal as JSON values: the same IDs in the same order, items, totals, counts, facet rows, histogram bars and positions. One faked clock serves both sides; a second check asserts that the device reads its clock once per read.
  - The library holds tracks with and without albums, editions, archived items and items outside the library, every recording grouping rule (shared ISRC within and beyond the duration span, an exact Last.fm link, a stored version group, durations from the track list), redundant and kept Last.fm placeholders, tags with aliases, identity keys, hidden tags, ancestors and descendants at several levels, artists with and without profiles, playlists of each source with import jobs in each state, library playlists of Tracks, Albums and Films (a playlist with entries listed twice, outside the library and removed, a smart playlist and a deleted one), films with credits and collections, plugin fields (text, number, a text key holding numbers, keys built in to one or both libraries, a Spotify audio feature), scrobbles at the edges of the rolling, monthly and yearly periods, in the future and at equal seconds, names shared by two tracks, case and accent variants, NFC and NFD forms, U+0130, Greek with a final sigma, a letter the database's `lower()` changes and one it leaves (both chosen at run time from the database, so the suite holds on any PostgreSQL version) in track titles, artist names and tag names, and nulls in every sortable field.
  - The matrix is generated from each library's `/fields`, so a new field is covered: every filter field in every mode with suggested, case-variant and absent values; Tags filters at Auto and at every level combination; search words (one to three words, short words, case, accents, labels); every range field with min, max, both and `includeMissing`, with fractional bounds and a bound inside a stored microsecond; every sort key in both directions paged to the last page, alone and under a filter, and the Tags sort at every location; `limitResults`; listening rules and the listening sort for each period kind (rolling days, weeks, months and years, date ranges, all time) with presence, absence and counts; histograms for each period; facets with no text, words and several words, every `tagLevels`, limits of 1, 3 and 50, with and without archived items, read before the facet vocabularies exist and from them; grouped Tracks with each sort and filters; positions; recordings lists; creator scopes; archived and edition toggles; Playlists sorts (`type`, `count` and `updated` included), sources and filters, and each of them with `library` for every library; every Playlists column filter without `library` (`owner`, `description`, `savedViewText` and `savedView`, `types`, `schedules`, each `columnRanges` column, `timeZone`, `keyNotation`), alone and with `q`; Films and Artists facets with `tagLevels`, which their services do not read; the `libraryPlaylist` filter in every mode on every library (alone, beside another filter, under a sort, in a histogram, a creator scope, grouped Tracks, positions and recordings), with a playlist of the library, of another library, a smart, a deleted and an unknown one; catalog scopes and queries the API rejects; text holding U+0000 (asserted to fall through with `nul-text` whatever the API answers, including the filters the service compares in TypeScript), other control characters or lone surrogates in `q`, filter values and the tag parameter of every read; malformed percent escapes.
  - Sampled rather than exhaustive: pairs of filters, 80 mixed pairs and 20 pairs in the any/unset group with a required filter per library, drawn with a fixed seed from the single-filter values.
  - It then makes edits through the services and routes (a track and an album title, a tag rename and re-parent, a track tag, an artist merge, a playlist member and rename, new scrobbles with their recount, an archive and a delete, a track leaving the library with a Sonovault tag that a library track would otherwise inherit, the only artist of an archived album credited on a listed album), renders the marks, syncs the changes and compares a reduced matrix: the same dimensions with fewer modes, values and periods and ascending sorts only.
  - It runs in CI in the integration shards, in a few minutes.
- DEVICE-33: The suite classifies every path from the Known holes (`integration/device-parity/holes.ts`, written from the table, not from the compiler; rows that depend on data recompute their condition from PostgreSQL for the data of each phase, so a fall-through is accepted only while its condition holds and a served answer is required when it does not). It computes the condition of every row for each read and expects the first reason the read holds in the order of reasons. A served answer for a listed shape fails; so does a fall-through whose reason is not the table's for that shape, and a path the resolver maps to no read that the API answers, except a path with a malformed percent escape, which the resolver leaves to the API whatever the API answers.
- DEVICE-34: Every key of every parsed query a read takes is named in a table beside its reader (`QueryKeys<Query>` in `compile/query-keys.ts`, collected by method in `deviceQueryKeys`), either `served` (the reader reads it, answering it as the service does or falling through with a reason of its own, or the service ignores it on every read the device answers) or `api`. The table's type names each key of the query type, so a key added to or removed from a schema fails `corepack pnpm typecheck` in `packages/library-source` until someone decides; `api` is the safe decision. A read whose query holds a value for a key not marked `served` answers `unimplemented-field`, second in the order of reasons. A value is anything but `undefined`: an empty array, string or object counts, and so would a schema default, so no key with a default is marked `api` (the unit tests assert it) and the web client's reads, which leave the unimplemented keys out, are served. The parity suite checks that each table names exactly its schema's keys, accepts `unimplemented-field` only for a read holding a key its table marks `api`, and reads each such key alone and with `q`.

## Stage 3: web client

- DEVICE-40: `fetchApiData` asks the device store first for a `GET` without a body when the setting is on, the copy is filled, the feed has accepted this page's session and no write is outstanding. A path that `mayBeLibraryRead` rules out (from the path alone, against the resolver's own route list) goes to the API at once, without waiting for the copy; the tab checks the others with `resolveLibraryRead` before asking the Worker. A served read is parsed with the caller's schema as an API answer is; an answer the schema rejects, a read the store does not serve, any store error and a read the Worker has not answered within five seconds go to the API unchanged. With the setting off nothing is installed: `fetchApiData` sends the same request as before, and no Worker, WebAssembly or store code is loaded.
- DEVICE-41: The store runs in one dedicated Web Worker, started by the one tab that holds the Web Lock `media-device-store`. SQLite on OPFS (`opfs-sahpool`) needs synchronous access handles, which a `SharedWorker` does not have, and only one Worker can hold the pool. Other tabs read from the API and take the lock over when it frees; reads are not passed between tabs. Messages are parsed with schemas on both sides. An aborted read rejects with the signal's reason, as a fetch does. Library reads at page start wait at most 1.5 seconds for the copy to open and the feed to accept the session, then go to the API.
- DEVICE-42: The setting "Library copy" is on the User page, saved in this browser, off by default, built from `Section` and `Segmented` like Key notation. A line under it states the state: opening, filling with the rows saved, waiting for the server's feed, ready with the time of the last sync (and the last failure), held by another tab, not available in this browser, or failed, with Retry. A failure is stated by its category, one fixed sentence each: the server's rows do not match the page's version, newer or older (reloading may fix it), the store's code did not load, the browser cannot store the copy, storage is full, the copy could not be read, the server could not be reached, or the copy could not be updated. The Worker sends the category, never an exception's text, and the store logs nothing. The driver discards the module's messages: Emscripten's through the init options `print` and `printErr`, and the library's logger (a failed statement's result code and SQL, the OPFS pool's I/O errors) through `globalThis.sqlite3ApiConfig`, whose `debug`, `log`, `warn` and `error` init reads and then deletes; a failure still throws from the call that met it, with its SQLite result code. Known limitation: when the module fails to start (its WebAssembly file cannot be loaded, or its bootstrap throws), the `@sqlite.org/sqlite-wasm` package's own code writes to the console directly ("Exception loading sqlite3 module", preceded by "sqlite3ApiBootstrap() error" or "sqlite3 bootstrap initializer threw" when the bootstrap failed), which no option controls. Turning it off, in this tab or another, deletes the local copy.
- DEVICE-43: Sync runs at start and when the setting is turned on, every 60 seconds while the tab is visible, when the tab becomes visible or the browser comes online, before Refresh reloads, and after every write through `fetchApiData`. A write in any tab of this browser holds reads on the API in the tab holding the copy from the moment it starts until a sync after it has settled reports no pending marks, so the refetches the write's own invalidations start read the API; player, Sonos, AI and ratings requests change no library row and do not hold reads. Each tab announces its writes' start and settling on the `BroadcastChannel` `media-device-store`, which opens only while the store runs; a write announced by a tab that closes before it settles stops holding reads after two minutes. A failed sync is retried with backoff, from 2 seconds up to 5 minutes, except when the feed's rows fail the client's schemas: the copy is then not ready, reads go to the API and nothing syncs again until Retry or the next page load; pending marks are read again from half a second. Refresh waits up to 10 seconds for its sync; if that sync fails, reads go to the API until one succeeds. A sync that changed rows refreshes the mounted library reads (query keys `tracks`, `albums`, `films`, `artists`, `playlists`, `listening-histogram`), except after a write or Refresh, which refetch already.
- DEVICE-44: Until the first fill completes, while the server's feed is not built, during a refill after a reset, while the feed's rows do not match the client's version (newer or older), and whenever the store is unavailable (no Worker, OPFS, Web Locks or WebAssembly, storage denied, quota), every read goes to the API.
- DEVICE-45: The store starts only on signed-in pages, those behind the session check, and on sign-in without a reload; signed-out pages load no store code and send no feed request. Sign-out deletes the local copy before navigation, waiting at most three seconds, and tells the tab holding it to delete it. A 401 from any API request, or a 401 or 403 from the feed, stops sync and deletes the copy. A copy left on disk serves again only after the feed has accepted the page's session.
- DEVICE-46: Browse performance samples carry `rowSource`, `device` or `api`, so local reads are not counted as API timings.
- DEVICE-47: No new visual element. The store's state is shown only under the setting. A sync or offline indicator elsewhere needs concepts and the owner's choice first.

Check in a browser at desktop and phone widths on the preview, after building the feed: with the setting on and filled, Tracks, Albums, Films, Artists and Playlists open, filter in each mode, search, sort, page and open facets with no API request for served reads, and the rows and counts match the same pages read through the API in a second tab. An edit shows its new value at once and later reads from the copy show it too. Sign-out and turning the setting off leave no local data.

### Order of reasons

A read can hold the conditions of several rows. The device checks them in this order and answers the first that holds; the parity suite expects the same (DEVICE-33).

1. `nul-text`, every read.
2. `unimplemented-field`, every read (DEVICE-34).
3. `not-ready`: the store has not completed a fill for this package's versions or holds no `fold` row. A filled store that lacks a row a read needs (a field list, the listening start, provider names) answers it when the read needs that row, after the reasons above it here.
4. `catalog-scope`, every Browse read.
5. `library-playlist`: Tracks, Albums and Films reads with a `libraryPlaylist` filter; Playlists reads with `library`.
6. `grouped-creator-scope`, Tracks.
7. `creator-films`, Films.
8. `invalid-query`: the field checks of Tracks, Albums, Films and Artists reads, against the synced field list: the sort, then each filter, then each range. Listening controls on Films are rejected by the route's schema, so they map to no read. A field the API accepts that the device's table cannot read answers `unknown-field` within these checks.
9. `unknown-field`: the sort by a plugin text field holding numbers, Albums and Films.
10. `provider-filter`, Tracks and Artists.
11. `creator-tag-sort`, Tracks.
12. `archived-artist-tags`, Albums facets.
13. `server-lower-case`, every read whose text the service lower-cases in TypeScript.
14. `active-import`, a Playlists page, decided from the page's rows.

`store-error` is not ordered: it is the answer to any failure of the store, wherever it occurs.
