# Tag and Collection Sources

Detail pages and modals retain label-click filtering and Shift-click keep-open behavior. The adjacent layers control opens a compact source-link popover, shared with the Tags table. It shows deduplicated relevant links with provider icons where available, plus a Manage tag action. Raw identifiers, merged names and detailed provenance belong in the management modal, not the popover. A collection with one known source uses an external-link control instead; multiple collection sources are listed separately. Source actions do not change filters or close media details.

`GET /api/v1/tags/provenance?mediaType=album&name=...&page=1&size=25` requires authentication and works within the selected album or film library. A `mediaId` can supply the media type instead and requires membership on that item; conflicting explicit context is rejected. Name-only requests without either context are invalid. It reads existing `media_item_tag` and `tag_occurrence` rows, groups equivalent names across original kinds within that medium, and paginates distinct sources. Item-specific origins come first; the compact popover omits origins marked as elsewhere in the same library. Library-wide provenance has no item-specific marker. More sources can be loaded without discarding the current links; the management modal exposes full provenance separately.

## One Tags Concept

### Visibility and Management

The Tags sidebar separates normal browsing from Hidden tags. Tables append rows on scroll rather than using Previous/Next controls. Checkboxes support Shift-range selection and deselection; the header checkbox selects loaded rows. Hide/unhide batches the complete selection without imposing a total selection cap. Manage tag opens the same detail modal from either a table row or a film source popover. Closing a nested tag modal returns focus to the film rather than closing it.

`GET /api/v1/tags` accepts `mediaType=album|film` (default `film`) and `visibility=visible|hidden|all` (default `visible`). Each tag summary includes `mediaType` and `hidden`. `POST /api/v1/tags/visibility` requires `{ mediaType, tagIds: string[], hidden: boolean }` (1-100 distinct IDs) and returns `{ updated, hidden }`, where `updated` counts changed displayed groups. Missing or other-medium IDs fail atomically with 404; already-merged source IDs fail with 409 so callers refresh instead of changing an unintended group. Merge requests likewise require `mediaType` alongside `sourceIds` and `targetId` and reject mixed-media selections.

Hiding affects the entire normalized name group across original kinds within one medium. An album tag never shares hidden state, merge targets, aliases or provenance with an identically spelled film tag. Hidden tags disappear from the normal tag list, media display tags, tag sorting values and autocomplete facets. Stored media membership, original source occurrences, aliases, merge audit and provider snapshots are retained. Existing explicit tag filters continue to match stored membership. Hidden groups remain manageable through `visibility=hidden`; unhiding restores them without importing again.

Imports reuse tag identities and never reset visibility. Merges use hidden-wins semantics: merging any hidden group makes the resulting canonical group hidden. Unhiding that canonical group explicitly restores it, including future imports of its aliases. Visibility writes share the existing advisory lock with merges and provider updates.

`GET /api/v1/tags/{id}?mediaType=album&page=1&size=25` requires the media type and returns `{ tag, aliases: [{ id, name, kind }], provenance }` inside the standard response envelope. Merged source IDs resolve to the current canonical group in that medium only. Sources reuse the existing paginated provenance response, including stored source links; no provider requests occur. Provenance includes `tagId` and `mediaType` for opening management from an item-specific source popover. Tags page URLs, query keys, merge search and All/Hidden links preserve the selected media type; changing it clears selections and tag detail state. Detail browse links target only the tag's own library.

Deployment requires `0010_overrated_ronan.sql` for visibility and `0011_tag_media_scope.sql` for isolation. Back up Postgres and quiesce old tag writers before applying `corepack pnpm --filter @repo/server migrate`. Keep desired schema and column-dependent consumers outside watched source until migration succeeds, then activate them together. An advisory lock serializes the migration with current tag writes but does not make old code compatible after commit. Do not reset or retry jobs as part of migration.

Migration 0011 splits the historical graph of same-name cross-kind tags, identities, aliases and merge audit edges into every medium it serves. Every membership and occurrence follows its media item. Shared album groups receive deterministic new IDs; film and album-only IDs remain stable. Unattached groups are retained in both media without invented memberships. Original hidden flags, names, kinds, actor/timestamps and raw provenance are preserved; provider payloads, normalized data and checksums are untouched. SQL guards reject cross-media associations, identities and merges, and prevent scope changes from invalidating existing relationships. After a failed migration, leave old code active: the transaction rolls back. Post-commit recovery requires a consistent backup and matching code, not a name-based down migration that would lose independent edits.

Tags, genres and keywords share one Tags field in album/film browsing, details, autocomplete, and film selection. The persisted field key remains `genre`; `keyword` and `tag` filter/sort URLs map to it for compatibility. Original kinds remain only in source provenance. Case, Unicode canonical equivalence and whitespace normalize consistently; unrelated names are not fuzzily combined.

The Tags page groups same-name rows within the selected medium, counts distinct media items, and shows actual merged names from `tag_alias`. Empty merge summaries are omitted. Explicit merges expand to every underlying row in the selected groups, retain all original occurrences and snapshots, and preserve aliases for subsequent imports. Cross-kind album merges are supported because all kinds now remain visible. Incoming same-name tags reuse existing identities across kinds only within their own medium. Browse aliases are resolved in the current library, never through another medium's merge graph.

Source links use genuine upstream IDs or name-based tag search URLs where supported. An opaque aggregator ID is never promoted to an upstream ID. IMDb namespace/name tags use its keyword search; TMDb keyword URLs require a genuine upstream keyword ID. Otherwise stored links, provider references or existing MDBList payload film IDs resolve a film URL. The link names the actual destination provider and example film, and explicitly labels a transporting-provider fallback. Global and merged origins use a film that actually contains that occurrence, never the unrelated film currently open. Missing supported URLs remain explained, not guessed.

MusicBrainz uses `https://musicbrainz.org/tag/{normalized-original-name}` for tag links, not a release or release-group page. The original occurrence name is normalized and URL-encoded for navigation; stored raw names remain unchanged after merges. Provider-specific tag links require supported structured evidence rather than an inferred upstream identifier.

Discogs uses its public field-based browse search: `https://www.discogs.com/search?genre=Electronic` or `https://www.discogs.com/search?style=Arena+Rock`. Both URL forms were generated and checked through the official [Advanced Search](https://www.discogs.com/search/advanced) browser UI, without API credentials or scraping. Discogs documents the distinct fields in its [genre/style guidelines](https://support.discogs.com/hc/en-us/articles/360005055213-Database-Guidelines-9-Genres-Styles) and [search guide](https://support.discogs.com/hc/en-us/articles/360003622014-How-To-Browse-Search-In-The-Database).

Legacy occurrence kind `genre` is not reliable Discogs classification: imports combined genres and styles. Provenance reads project only saved `genres`/`styles` from raw records, `master`, `release`, and `mainRelease`, including the Discogs section of `legacy-record` snapshots. Exact normalized original names determine the query field; when both fields contain the name, the query retains both proven filters. Evidence is scoped to the origin's example item, not a different album currently open. Explicit `style` occurrences can link directly without a snapshot; unclassified legacy genres are not guessed. Proven direct links take precedence over saved album/master links. No snapshots or occurrences are rewritten and no provider requests run. AUDACITY (`album_5cb714869b443db9ec5e`) verifies Electronic/Pop as genres and Alt-Pop/Dance-pop as styles; legacy Arena Rock resolves from `master.styles` despite its stored genre kind.

The [offline provenance repair](tag-provenance-backfill.md) restores proven album and film origins from retained structured snapshots. It preserves original unknown occurrences for audit. Read responses omit such an unknown placeholder only when an attributed occurrence exists for the exact same media item, tag ID, normalized raw name and original kind. Tag-table source counts/previews and paginated provenance use the same predicate. Unknown origins from other items, other merged names, other kinds, or with opaque source IDs remain visible; no stored row is deleted.

TMDb genre and keyword IDs can also be recovered from current payloads and older snapshots for that origin's film. Reads project only genre/keyword arrays. Matching requires the same original kind and normalized original name; an explicitly TMDb-namespaced aggregator slug can match its space-separated name. Conflicting IDs remain unresolved. Recovered links are labelled, while original occurrence IDs and snapshots remain unchanged. New TMDb genre results retain `source`, `sourceId` and `rawName` just like keywords. The [TMDb Drama genre page](https://www.themoviedb.org/genre/18-drama/movie) illustrates the ID-based genre URL.

Saved link ownership is not destination identity: an aggregator can own a Metacritic link. Fallbacks validate the destination hostname and prefer verified film IDs over owned links. An MDBList-labelled link must point to MDBList, never another rating site merely because MDBList imported it.

MDBList's [keyword documentation](https://docs.mdblist.com/docs/keywords) distinguishes upstream sources and custom tokens. The [public IMDb-ID film route](https://mdblist.com/movie/tt0111161) resolves to MDBList's film page, so it can be derived from a stored IMDb film ID. This is not an IMDb keyword ID. IMDb's [keyword search](https://www.imdb.com/search/title/?keywords=search) supports a name query. These public pages were checked without API credentials; no private site requests or scraping were performed.

Detail responses expose optional `collectionSources` links. Generic plugin templates resolve rich collection IDs, and the pure stored-payload hook described in `local-plugins.md` handles older imports. Neither browsing nor expanding provenance performs provider requests or writes data. Collection names without saved identifiers cannot be linked reliably and remain filters.

Native popovers use the top layer inside media dialogs, keep source content scroll-contained, return keyboard focus on close, and intercept Escape without dismissing the parent modal. Provenance loads only when opened and offers retry and additional pages. Browse/grid virtualization is unchanged.

Offline verification covers source URL validation, template encoding, opaque IDs, existing payload readers, tag merge attribution and pagination in temporary Postgres, authenticated route validation, and source-list rendering. Browser acceptance: open a collection link, expand a multi-origin tag, press Escape, then Shift-click its label; filters and media modal state must stay correct.

## Query Performance

Migration `0013_tag_membership_lookup.sql` adds a covering `(tag_id, media_item_id)` membership index. The original primary key begins with media item ID and cannot efficiently serve tag-table item counts. The migration is additive and preserves all tag data and provenance.

Tag listing uses a window count so ordinary pages do not repeat the normalized grouping query. Empty/out-of-range pages retain an explicit count fallback. Search joins a distinct set of matching canonical names, original occurrence names and identities, then filters whole normalized groups. Do not replace this with per-group correlated searches or an `IN` subplan: broad matches can exceed PostgreSQL's hash memory budget and degrade into repeated scans. Search escaping, medium isolation, hidden groups, aliases, distinct item/source counts and the 20-source preview remain unchanged.

The integration regression fixture exercises broad name and provenance searches over 12,000 tags with a 64 kB work-memory budget and a five-second per-statement timeout, alongside 50,000 memberships. Local verification on 2026-10-28 compared full responses before/after on the existing library (roughly 93,000 tags and 518,000 memberships), including film/album lists and searches. No provider requests or caches are involved; all reads remain current.
