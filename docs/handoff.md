# Project handoff

Start here when picking up work without the original conversation. The [requirements](requirements/README.md) describe what to preserve; the [documentation index](README.md) links to setup and repair instructions. Counts and release decisions quoted in the guides are dated evidence, not live status.

## What the app is

This is an owner-only film and album library. PostgreSQL is the source of truth; JSON, CSV and NFO files are import inputs, not runtime databases. The rebuild follows the CSDR layout: Next.js App Router for the web app, Hono and Better Auth for the API, Drizzle for persistence, and shared schemas and a plugin SDK. Private sources belong in local packages, not tracked code, fixtures or docs.

The main workflow is **browse, open an item, then drill down**. Keep table/grid navigation, virtual scrolling, clickable filters and separate film/album workspaces intact. On albums, Spotify is the main listening destination, not an identity system. Saved-album discovery uses the date saved, not listening history. Playback controls and Spotify audio features are intentionally out of scope. See [browsing](requirements/browsing.md), [filter interactions](requirements/search.md) and [album requirements](requirements/music.md).

Imports and provider lookups are different operations. Preview files before writing, reconcile identifiers before creating a new film, and queue metadata for newly imported films, not every row in a CSV. A missing identifier is a visible correction task. A scrape job is **one provider and one media item**. Multi-selection creates multiple jobs; it does not change that relationship. Provider concurrency controls how many can run. See [imports](importing.md), [jobs and safety](requirements/imports-and-plugins.md) and [film Added dates](nfo-creation-dates.md).

## How scraped data combines

- **Identity:** Albums and films have internal IDs. A provider identifier points to the item; it is not its primary key. A user can correct the identifier and request a new scrape without creating another library item.
- **Evidence:** A successful scrape stores the provider payload and its normalized result, links the snapshot to the job and advances that provider's current state for the item. Scrapes retain history even if the payload repeats. File and legacy imports can reuse an identical prior snapshot. Failed jobs can have diagnostic JSON without a successful snapshot: inspect the job itself. A failed attempt, a never-attempted lookup and a match with no score are different outcomes.
- **What appears in the app:** The [provider-state writer](../apps/server/src/services/provider-state.ts) applies normalized patches to shared media, album and film records. An incoming browse key generally replaces the previous value for that key, not the whole browse object. Manual overrides on supported fields win. Different rating sites have distinct fields, but two providers reporting the same site's score do not participate in a general source-priority or freshness rule. The owner explicitly deferred redesigning this; do not assume the displayed score and vote count always came from the same scrape.
- **Tags:** Tags and keywords share a browsing concept **within** a library, never across albums and films. A merged display tag can have multiple original labels and provider occurrences. Preserve that evidence and link to the provider's tag or collection when possible, not merely the release that supplied it. See [source navigation](tag-source-navigation.md) and [film keyword sources](film-keyword-providers.md).
