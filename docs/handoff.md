# Application architecture

See the [requirements](requirements/README.md) for expected behavior and the [documentation index](README.md) for setup and maintenance.

## What the app is

### Catalog records and library membership

Albums, tracks and films have one detail address from first discovery. An exact provider identity can resolve to an existing record. A provisional record uses its source context to distinguish otherwise identical names. `media_item.in_library` controls admission. An explicit addition updates the existing row and records the addition date. A playlist position records separately whether it grants library membership. People, artists, playlists, collections and subscription resources can also be saved independently. Saving a video leaves the channel's subscription setting intact.

`catalog_observation` retains each attributable discovery, including its target, originating subject, operation, position and available response, job, snapshot or import evidence. The Sources tab reads these observations. Replaying a retained occurrence uses its original key. The album-track merge journal preserves old track addresses and discovery evidence across undo and redo.

The default Browse scope is **In library**. **Outside library** lists discoveries and **All known** includes both. With **All known**, selecting an origin keeps members and narrows outside rows. **Apply source filters to library items** narrows members as well. The scope and origin settings travel with the URL.

Opening a known Spotify album with missing details can request that exact album. On an artist's Albums tab, the explicit listing action checks the artist identity and saves Spotify release pages with their offsets. A retry can continue after the last saved page. See [development](development.md#replaying-catalog-discoveries) for offline recovery.

This is an owner-only film and album library. PostgreSQL is the source of truth; JSON, CSV and NFO files are import inputs, not runtime databases. The rebuild follows the CSDR layout: Next.js App Router for the web app, Hono and Better Auth for the API, Drizzle for persistence, and shared schemas and a plugin SDK. Private sources belong in local packages, not tracked code, fixtures or docs.

The main workflow is **browse, open an item, then drill down**. Keep table/grid navigation, virtual scrolling, clickable filters and separate film/album workspaces intact. On albums, Spotify is the main listening destination, not an identity system. Saved-album discovery uses the date saved, not listening history. Listening history comes only from the optional [Last.fm scrobble sync](lastfm-scrobbles.md), an account-level sync that runs as Last.fm jobs. Optional [in-app Spotify playback](spotify-playback.md) is off until connected in Providers. Its queue and session are saved for the account (`/api/v1/playback`, one `PlaybackSessionStore` Durable Object per user), so a reload or another signed-in browser carries on with them. An optional [Sonos connection](sonos.md) (`/api/v1/sonos`, account-level provider `sonos`) stores a Sonos account's tokens on the server, lists its rooms and lets the player play Spotify on Sonos rooms and control them. Tracks the player loads on a room can be [scrobbled to Last.fm](sonos.md#scrobbling-to-lastfm) through a Last.fm sign-in stored the same way (`/api/v1/lastfm/scrobbling`, `/api/v1/lastfm/scrobbles`); nothing else the app plays or shows is scrobbled. Tracks are a third library beside albums and films. Stored album track lists, imported Spotify playlists, Liked Songs and stored Last.fm history share the same track items. Source filters can include or exclude each membership, and a track can have several sources. **Tracks → Imports → Last.fm scrobbles** shares the album history sync; completing a sync updates tracks automatically. **Refresh matches** reuses stored history after metadata changes. Track details show recorded names and where their Spotify identity came from; confirmed merges preserve manual choices across later syncs. Merges of tracks, albums and artists, and the matches automatic rules make, are recorded in one change journal with Undo; a merge keeps Spotify tracks as versions and albums as editions. See [library merges](library-merge-handover.md). A track is a media item of its own type, whose album and playlist memberships each preserve their own order. It links to stored scrobbles and can have a Spotify ID. Tracks project album tags and can supplement sparse release tags with artist tags; Track Sources, Tracks → Jobs → Metadata and the Last.fm import table can queue a Spotify catalog search for an unmatched recording. Each job automatically links a compatible title and artist match. When several Spotify editions fit, the matcher prefers an observed or library release, then uses the artist credits, available track popularity and Spotify result order. Conflicting identities remain available for review. See [tracks and Spotify playlists](tracks-and-playlists.md). Spotify audio features are intentionally out of scope. [TIDAL](album-providers.md#tidal) is a catalogue and matching source only: an album match by the Spotify UPC aligns the track list, a track match finds one track by ISRC, both run in the request that asks for them through the TIDAL request gate, and both store `tidal` `track` and `isrc` references on library tracks; nothing plays through TIDAL. [Sonovault](album-providers.md#sonovault) is a paid lookup provider for track identifiers: a task job sends library tracks, by Spotify track ID or ISRC, in bulk requests, and stores the IDs it reports on other services as `sonovault` `provider_reference` rows, checked against the library track and removable in one action; it never changes another provider's identifiers. The album and track drawers' Similar tab lists TIDAL's similar albums or tracks, read from TIDAL in the request for that item and mapped to library items by ISRC or UPC or to Spotify by a Sonovault bulk lookup of track ISRCs and a Spotify lookup job for the rest, so they play through Spotify ([similar items](album-providers.md#tidal)). See [browsing](requirements/browsing.md), [filter interactions](requirements/search.md) and [album requirements](requirements/music.md).

Imports and provider lookups are different operations. Preview files before writing, reconcile identifiers before creating a new film, and queue metadata for newly imported films, not every row in a CSV. A missing identifier is a visible correction task. A scrape job is **one provider and one media item**. Multi-selection creates multiple jobs; it does not change that relationship. Task jobs record their subject in their scope: Last.fm scrobble sync and the Spotify playlist listing target the account, a Spotify playlist import targets one playlist or Liked Songs, a Spotify album addition targets one album and one playlist, a Spotify album search targets one explicitly selected scrobbled artist/album group, a Spotify track search targets one library track, and artist enrichment targets one artist and one provider. A task job can record its progress in `options.progress`. Jobs, job pages and provider pages name a job by its action and subject (`jobTaskTitle` in `apps/web/utils/job-selection.ts`); a task job whose options name a library item gets that item's current title and artists when it is loaded (`apps/server/src/services/job-subjects.ts`), and a batch is named by the task all its jobs run. Album search candidates stay attached to their scrobbled artist/album group until the owner chooses an album to add or link. Provider concurrency controls how many can run. See [imports](importing.md), [jobs and safety](requirements/imports-and-plugins.md) and [film Added dates](nfo-creation-dates.md).

The optional [Subscriptions library](subscriptions.md) is a separate choice in the library selector with Browse, Channels and Imports pages; Jobs and Providers filter to it with their Library filter. It stores YouTube channels and Spotify podcasts in `subscription_source`, their videos and episodes in `subscription_item`, and one sync checkpoint per account and provider in `subscription_sync`, not as media items: it has no scrape snapshots, tags or imports. Each row's type is its provider, and every sync reads and changes only its own type. `/api/v1/subscriptions` browses both types with the other libraries' filter, range and sort parameters; `/api/v1/youtube` serves the YouTube account connection. The YouTube sync is an account-level YouTube task job; the Spotify podcast sync (`spotify-podcast-sync`) is an account-level Spotify task job that reads saved podcasts and their episodes into the same tables. Both sync jobs are listed only in this library's Jobs (`mediaType=subscription`, decided by the job's task). Search reads only stored rows through a PostgreSQL full-text index. Providers marked `subscriptions` in the catalog (YouTube and Spotify) are listed in this library's Providers; the YouTube provider has no media types, so it is not listed for albums or films, and the hosted runtime starts its dispatcher unpaused.

The optional [Mixes library](mixes.md) is another choice in the library selector with Browse, Shows and Imports pages. It stores radio station archives in the Subscriptions tables: a station show is a `subscription_source` and a mix a `subscription_item`, with the billed artists, a page URL and a recording URL. A row's type decides its library (`youtube` and `spotify` are Subscriptions; `rinse`, `nts` and `lotradio` are Mixes), and `/api/v1/subscriptions` reads one library per request (`library=mixes`). Each station is a provider without credentials, read through one adapter contract (`apps/server/src/lib/mix-station.ts`) by one sync engine; its sync is a task job listed only in this library's Jobs (`mediaType=mix`), and providers marked `mixes` in the catalog are listed in this library's Providers. Mixes are links only. Billed artist names match library artists by name when a page is read, and the Tags filter reads the album tag hierarchy; neither creates artists or tags.

Artists have a separate library selector entry with Browse, and artist metadata selection is Jobs → Metadata with the Artists library filter, sharing the existing `artist` and `media_credit` identities across Albums and Tracks. Browse and metadata selection support stored-playlist filters. Artist jobs are scoped by their task, including legacy jobs stored with the album scope, and metadata selection shows per-provider scrape dates and freshness filters. Film People exposes director and actor roles. Channels retain subscription source IDs. Their names open details in the shared inspector with history, related library items and explicit filter actions. Artist provider snapshots remain separate from release snapshots. Artist tags supplement fewer than two visible album tags at read time without copying tag memberships. See [artists, people and channels](artists-and-people.md).

## How scraped data combines

- **Identity:** Albums and films have internal IDs. A provider identifier points to the item; it is not its primary key. A user can correct the identifier and request a new scrape without creating another library item.
- **Evidence:** A successful scrape stores the provider payload and its normalized result, links the snapshot to the job and advances that provider's current state for the item. Scrapes retain history even if the payload repeats. File and legacy imports can reuse an identical prior snapshot. Failed jobs can have diagnostic JSON without a successful snapshot: inspect the job itself. A failed attempt, a never-attempted lookup and a match with no score are different outcomes.
- **What appears in the app:** The [provider-state writer](../apps/server/src/services/provider-state.ts) applies normalized patches to shared media, album and film records. An incoming browse key generally replaces the previous value for that key, not the whole browse object. Manual overrides on supported fields win. Different rating sites have distinct fields, but two providers reporting the same site's score do not participate in a general source-priority or freshness rule. Do not assume the displayed score and vote count always came from the same scrape.
- **Tags:** Tags and keywords share a browsing concept **within** a library, never across albums and films. A merged display tag can have multiple original labels and provider occurrences. Preserve that evidence and link to the provider's tag or collection when possible, not merely the release that supplied it. Tags can have parent tags within their library (`tag_parent`, with `tag_ancestor` holding every tag above each tag); a filter on a tag also matches the visible tags beneath it. See [source navigation](tag-source-navigation.md), [tag hierarchy](tag-hierarchy.md) and [film keyword sources](film-keyword-providers.md).
