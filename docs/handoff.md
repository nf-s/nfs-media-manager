# Application architecture

See the [requirements](requirements/README.md) for expected behavior and the [documentation index](README.md) for setup and maintenance.

## What the app is

This is an owner-only film and album library. PostgreSQL is the source of truth; JSON, CSV and NFO files are import inputs, not runtime databases. The rebuild follows the CSDR layout: Next.js App Router for the web app, Hono and Better Auth for the API, Drizzle for persistence, and shared schemas and a plugin SDK. Private sources belong in local packages, not tracked code, fixtures or docs.

The main workflow is **browse, open an item, then drill down**. Keep table/grid navigation, virtual scrolling, clickable filters and separate film/album workspaces intact. On albums, Spotify is the main listening destination, not an identity system. Saved-album discovery uses the date saved, not listening history. Listening history comes only from the optional [Last.fm scrobble sync](lastfm-scrobbles.md), an account-level sync that runs as Last.fm jobs. Optional [in-app Spotify playback](spotify-playback.md) is off until connected in Providers and keeps its queue in the browser only. Tracks are a third library beside albums and films, filled by imported Spotify playlists, Liked Songs and stored Last.fm history. Source filters can include or exclude each membership, and a track can have several sources. **Import Last.fm tracks** uses stored history without provider requests; completed syncs and relinking also refresh it. A track is a media item of its own type that links to its library album and to stored scrobbles; its Spotify ID may be null, and it is never scraped, tagged or added merely by an album's track list. See [tracks and Spotify playlists](tracks-and-playlists.md). Spotify audio features are intentionally out of scope. See [browsing](requirements/browsing.md), [filter interactions](requirements/search.md) and [album requirements](requirements/music.md).

Imports and provider lookups are different operations. Preview files before writing, reconcile identifiers before creating a new film, and queue metadata for newly imported films, not every row in a CSV. A missing identifier is a visible correction task. A scrape job is **one provider and one media item**. Multi-selection creates multiple jobs; it does not change that relationship. Task jobs have no library item: Last.fm scrobble sync and the Spotify playlist listing target the account, a Spotify playlist import targets one playlist or Liked Songs, a Spotify album addition targets one album and one playlist, and a Spotify album search targets one explicitly selected scrobbled artist/album group. A task job can record its progress in `options.progress`. Search candidates stay attached to that group until the owner chooses an album to add or link. Provider concurrency controls how many can run. See [imports](importing.md), [jobs and safety](requirements/imports-and-plugins.md) and [film Added dates](nfo-creation-dates.md).

The optional [Subscriptions library](subscriptions.md) is a separate choice in the library selector with Browse, Channels, Imports, Jobs and Providers pages. It stores YouTube channels and Spotify podcasts in `subscription_source`, their videos and episodes in `subscription_item`, and one sync checkpoint per account and provider in `subscription_sync`, not as media items: it has no scrape snapshots, tags or imports. Each row's type is its provider, and every sync reads and changes only its own type. `/api/v1/subscriptions` browses both types with the other libraries' filter, range and sort parameters; `/api/v1/youtube` serves the YouTube account connection. The YouTube sync is an account-level YouTube task job; the Spotify podcast sync (`spotify-podcast-sync`) is an account-level Spotify task job that reads saved podcasts and their episodes into the same tables. Both sync jobs are listed only in this library's Jobs (`mediaType=subscription`, decided by the job's task). Search reads only stored rows through a PostgreSQL full-text index. Providers marked `subscriptions` in the catalog (YouTube and Spotify) are listed in this library's Providers; the YouTube provider has no media types, so it is not listed for albums or films, and the hosted runtime starts its dispatcher unpaused.

## How scraped data combines

- **Identity:** Albums and films have internal IDs. A provider identifier points to the item; it is not its primary key. A user can correct the identifier and request a new scrape without creating another library item.
- **Evidence:** A successful scrape stores the provider payload and its normalized result, links the snapshot to the job and advances that provider's current state for the item. Scrapes retain history even if the payload repeats. File and legacy imports can reuse an identical prior snapshot. Failed jobs can have diagnostic JSON without a successful snapshot: inspect the job itself. A failed attempt, a never-attempted lookup and a match with no score are different outcomes.
- **What appears in the app:** The [provider-state writer](../apps/server/src/services/provider-state.ts) applies normalized patches to shared media, album and film records. An incoming browse key generally replaces the previous value for that key, not the whole browse object. Manual overrides on supported fields win. Different rating sites have distinct fields, but two providers reporting the same site's score do not participate in a general source-priority or freshness rule. Do not assume the displayed score and vote count always came from the same scrape.
- **Tags:** Tags and keywords share a browsing concept **within** a library, never across albums and films. A merged display tag can have multiple original labels and provider occurrences. Preserve that evidence and link to the provider's tag or collection when possible, not merely the release that supplied it. See [source navigation](tag-source-navigation.md) and [film keyword sources](film-keyword-providers.md).
