# Library query performance

Library search keeps case-insensitive substring matching: every word must match a text value, and different words can match different fields. Search and autocomplete read stored library rows only.

## Performance review for a feature

1. List the API calls for a cold browser visit and for the interaction being changed. Include authentication, shell polling, exact totals and requests that continue after closing a control. Identify which calls block the first usable result.
2. Capture the SQL through the real service entry point on the supported PostgreSQL versions. Use synthetic data with common and rare values, ties and skew. Exercise a selective hit, a miss, a broad result, a deep page and a write immediately followed by a read where applicable. Verify the result IDs, counts, ordering and visibility.
3. Measure the whole operation and the database work separately. Record statements per request, serial round trips, logical shared blocks and temporary blocks. Repeat the service call on a warm connection and after invalidating any derived data. For an index, compare representative reads with and without it, including a broad query, and account for index size and writes.
4. Add the representative workload and its ceiling to the performance suite. A budget change needs the old and new measurements and a reason. Include an interaction test when request fan-out, cancellation or visibility changes. The CI log records the measured plans' work for each tested workload.
5. After deployment compare successful requests from the same route and query shape against their previous window. Report elapsed time, median, p95, sample count and errors. An empty window is unmeasured. Capture frontend timings separately when the browser still feels slow.

### Running the regression check

Run the following from a checkout with the normal local test environment and a disposable PostgreSQL server.

```sh
corepack pnpm --filter @repo/server test:performance
```

CI runs the suite on PostgreSQL 17 and 18 for pushes, pull requests and the nightly schedule. The suite builds a synthetic library, refreshes planner statistics, runs the service, and replays its captured reads with `EXPLAIN (ANALYZE, BUFFERS, TIMING OFF, FORMAT JSON)`. It sums hit and read blocks from each root plan. Child nodes are already included. It checks response semantics, bounds logical work and detects a spill to temporary storage. Elapsed execution time in the log helps diagnose changes. Cloud networking, authentication and browser rendering are measured separately. Add new workloads to `integration/*.performance.ts`. [PostgreSQL EXPLAIN guide](https://www.postgresql.org/docs/17/using-explain.html)

### Continuous production monitoring

CI also runs the packaged API Worker locally with production settings and synthetic bindings. The build must start and serve its healthcheck before the checks pass. This catches module initialization failures that TypeScript and a bundle-only build can miss.

For browser latency, filter the API Worker's structured events to `browser.browse`. Group by `screen`, `action` and `outcome`. Report volume and visible-result duration for Tracks, Albums, Artists, Films, Playlists, Collections and Subscriptions. Track, Album and Artist detail openings also report a `detail` action. Look at errors separately. The browser sends fixed categories and elapsed milliseconds only. Make the same foreground measurement part of the acceptance check for a new Browse or detail screen.

The `document` action starts at document navigation when the browser can verify it stayed visible. An in-app `open` or `detail` starts when the screen first commits. A `change` starts when the new query is committed, and `page` starts when scrolling exposes an unloaded leading page. Each ends after a paint opportunity for the rows, empty state or terminal error. Hidden and superseded interactions are discarded. Monitor cold document opens separately from in-app opens. Count abandoned interactions, time spent typing and delays before an in-app screen mounts as gaps in this measurement. Start with a daily p95 target of 2.5 seconds for cold documents and one second for in-app interactions when a group has at least 20 samples. Investigate foreground samples over five seconds even at low volume. Compare daily medians and p95 by action and screen alongside the corresponding server route.

For slow Track details, compare the `trackDetailHydrate`, `trackDetailListening`, `trackDetailNames` and `trackDetailAlternate` phases on `api.request`. The latter three can overlap. The alternate lookup runs only when the track needs a playable sibling. For Album details, independent reads run in bounded batches to reduce round trips.

The API emits one `api.request` access event per completed handler invocation. In Workers Query Builder, select the API Worker and filter by this event. Group by the registered `route` and `method`. For successful interactive reads, show count, median, p95 and maximum of `durationMs`. Count server errors in a separate series covering all statuses. Get the traffic count before adding optional phase fields. Query each applicable phase separately so missing fields do not exclude requests from the denominator. Start with the following alert thresholds and recalibrate from measured traffic when usage or capacity changes. [Cloudflare Query Builder](https://developers.cloudflare.com/workers/observability/query-builder/)

| Browse page          |                 750 ms |
| Exact Browse count   |               1,000 ms |

Review the preceding 24 hours once a day. Require 20 successful requests before interpreting a route's p95. Investigate individual foreground requests above five seconds and server errors even at lower volume. On a quiet installation, also flag two or more foreground page requests of the same route and query shape over two seconds in one day. Report how many crossed that threshold and their slowest phase. - `durationMs` measures API entry to response creation, including the Worker database pool lifecycle. `drizzleStatementCount` counts attempted Drizzle statements including prepared execution. Direct driver calls and PostgreSQL internal work are outside the count.
- `phases.accessCheck` times credential resolution. Tracks, Albums and Films Browse report `phases.ids` for selecting page IDs and `phases.hydrate` for loading the returned rows. Media Browse exact counts use `phases.count`. Facets report `phases.facets` and distinguish a vocabulary read, foreground rebuild attempt and live aggregation using `facetRead`, `facetBuild` and `facetLive`. Each phase includes elapsed time and its directly attributed statement count. Nested or parallel times can overlap.
- The media Browse `browse` object groups requests by grouped recordings, page depth, filtering, listening and sort family. For play-count ordering, `browse.playSort` distinguishes stored scrobbles from a count computed for the selected listening period. The `browse.listeningUse` field distinguishes a listening filter, a requested period count, or both. Use `browse.sortField`, `browse.filterFields`, `browse.rangeFields` and `browse.searchTerms` to reproduce a slow combination with synthetic values. These fields distinguish built-in field names and single-word or multiword searches. Extension fields are grouped as `other`. Compare the PostgreSQL query identifier for a synthetic `EXPLAIN (VERBOSE)` with the slow statement fingerprint to confirm the query shape without reading search text. If authentication or many small statements dominate, inspect connection setup and dependent round trips. If API durations are healthy, trace the frontend's request waterfall and render time.
- For grouped Tracks, split the same page depth and listening shape by `browse.recordingOrderLookup`. A `hit` means the request found a current generation. Filtered pages can reuse its visible group membership and still compute their own ranks. A `miss` can lead to a refresh or a live query. Inspect the query plan for slow hits as well as misses.
- For grouped Track pages and counts with listening rules, `browse.listeningRules` records one or multiple rules, all or any matching, the period kind or mixed kinds, and whether the thresholds ask for presence, absence, both presence and absence, numeric counts, or a mix of presence and numeric counts. Combine the categories with `browse.listeningUse` when a requested period column also needs counts. Dates, rolling window lengths, threshold values and identifiers stay out of the log.
- For filtered Track pages, `browse.creatorScoped` identifies requests for a creator's library without logging an identifier. Compare those requests separately from searches across the full library, including at the default Title sort. The page and its independent exact count check artist credit before looking up duplicate Last.fm source rows. The performance suite exercises both small and large artist catalogs, including release-order ties.
- After a grouped Tracks miss, check the next `database.recording-order-maintenance` event. Its `source` distinguishes a refresh requested by Browse from scheduled maintenance. The Worker can rebuild an eligible invalidated order after returning the page or count, using a fresh database connection. Concurrent requests share a database lease. If writes continue during the build, reads still check for committed changes and fall back to the exact query.
- Cloud deployments run one daily `database.probe` at 20:00 UTC on a fresh invocation pool. It records the time for the first `SELECT 1`, including connection setup. The `database.facet-maintenance`, `database.album-facet-maintenance`, `database.recording-order-maintenance` and `database.duplicate-maintenance` events record whether the scheduler published the Tracks and Albums autocomplete vocabularies, grouped recording order or possible duplicates, skipped a refresh or failed. Compare those outcomes with foreground reads in the same interval. Treat failed probes or no successful probe over 26 hours as a monitoring incident even during quiet traffic.
- Use aggregate views of fixed route templates and bounded field values. Keep query text, bind values, requested URLs, headers, row contents and personal identifiers out of performance measurements. PostgreSQL's optional `pg_stat_statements(showtext := false)` can identify costly statement IDs from changes in calls, total execution time and shared blocks between snapshots. It requires the extension and permission. Counters can reset and do not supply a p95. [PostgreSQL statement statistics](https://www.postgresql.org/docs/17/pgstatstatements.html)

### Sampling production SQL work

Use the read-only sampler from an operator environment configured with the application database role. PostgreSQL 17 or newer and the `pg_stat_statements` extension are required. On an installation with the module preloaded, the database administrator can enable the extension in the application database with `CREATE EXTENSION IF NOT EXISTS pg_stat_statements`. The sampler does not install an extension or change privileges.

```sh
corepack pnpm --silent --filter @repo/server db:sample-statements --seconds 30 --limit 20
```

The JSON report ranks opaque statement fingerprints by execution time accumulated between two snapshots. It includes calls, shared blocks and temporary block counts when available. It filters to the connected role and database and never selects statement text. It reports counter resets and excludes invalid deltas. Use it while a specific operation is active to distinguish a single costly statement from many inexpensive calls. Multiple clients using the same role contribute to the same sample.

## Queries and indexes

Search finds matching media IDs through field-specific queries. Titles, summaries, artists, playlists and tags are searched before their memberships are joined. This lets PostgreSQL use `pg_trgm` GIN indexes instead of constructing related JSON values for every library item. The same field sources serve autocomplete, preserving whole-library counts and per-field limits. Track source and match-status labels use separate branches so an unrelated search word does not calculate playback matches for every track.

| Query                                     | Index coverage                                                                                             |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Title and summary substrings              | Trigram indexes on `media_item.title` and `summary`                                                        |
| Artist and credit suggestions             | Trigram artist names and `(artist_id, role, media_item_id)` membership lookup                              |
| Playlist and collection suggestions       | Trigram playlist names; existing playlist membership indexes                                               |
| Track album names                         | Trigram stored album names and media titles                                                                |
| Tags and original labels                  | Trigram display names, normalized names, identities and occurrence labels; existing tag membership indexes |
| Title ordering                            | Existing `(media_type, lower(title), id)` index, using the column directly                                 |
| Default track and film ordering           | Added-date index supplies the track order before album ties; release-date index supports film date and ID  |
| Track album-list matching                 | Album ID plus the exact normalized-title expression                                                        |
| Rolling Track listening presence          | Composite `(track_key, artist_key, listened_at, username)` supports bounded name/time probes               |
| Album listening date windows              | Partial `(listened_at, album_media_item_id)` index for linked scrobbles                                    |
| Subscription text search                  | Existing full-text GIN index on `subscription_item.search`                                                 |
| Subscription title and source suggestions | Trigram indexes on item and source titles                                                                  |
| Subscription duration ranges              | Index on `nullif(duration_sec, 0)`, matching the query's treatment of unknown durations                    |
| Artist freshness and latest attempt       | Partial provider/artist-ID/descending-time indexes for artist enrichment jobs                              |
| Artist name ordering                      | B-tree on `lower(coalesce(sort_name, name)), id`                                                           |
| Artist scrobble ordering and ranges       | Stored `artist.scrobble_count` with a B-tree on `scrobble_count DESC NULLS LAST, id`                       |
| Job history and batch lookup              | Descending creation date and ID, plus the batch ID expression                                              |

Indexes are targeted at stored columns and query expressions. Generic JSON metadata expansion and broad aggregate reports still need to process matching rows. Very short substring searches and common words can match much of a library; a trigram index is most useful when the search contains selective runs of at least three characters. PostgreSQL can choose a sequential scan when that is cheaper.

## Browse pagination

Albums, Films, Tracks, Artists and Subscriptions expose `/api/v1/{library}/browse-page` for rows and `/api/v1/{library}/browse-count` for the exact filtered total. The first returns `items`, `page`, `size` and `hasMore`. It reads one extra result to detect continuation and respects the result cap where the library supports one. The second returns `totalCount` from the same membership predicate and reuses the short-lived, database-versioned cache. It also returns `unfilteredCount`, the library's total without search, filters or ranges, which the toolbar shows as `N of M` while a filter is active. The original paginated routes still return rows and totals together.

`GET /api/v1/tracks/positions` returns the tracks at up to 50 given positions of a track query's order. It numbers the ordered rows once, as far as the deepest position asked for, and hydrates only the rows at those positions. Shuffled playback uses it because a page per random position orders the whole result again for every track; on a large list one such read costs about as much as a single deep page.

Ungrouped Title pages check redundant Last.fm sources as they read the tracks. Deep Title pages and position lookups can apply visibility during the primary title index scan, then resolve artist, album and track-position order only for the titles tied with the requested ranks. The page and position reads use the same visibility rules as the independent count.

Browse can display the first page and expand the scroll area when the total arrives. A first page with `hasMore: false` already gives the total. Later pages skip counting, including when a requested page is empty. A failed count can be retried while the loaded page remains available.

Grouped Tracks Browse checks full titles, artist credits and durations only for tracks that could share a recording. Tracks without a possible match use their stored listening totals directly. Sorting by listening or Added first identifies rows within the requested rank, including ties. The usual release ordering then resolves those ties. Expanding one recording reads candidates for its title. The server caches a bounded page of grouped IDs and listening totals and checks the database snapshot before reuse, including after another process imports or edits a track.

On a disposable fixture of 63,000 tracks, fetching the first grouped page sorted by scrobbles, including track details, took about 400 ms compared with 2.16 seconds before the optimization. The uncached grouped count took 250 ms compared with 1.02 seconds. These are service timings on synthetic data.

Artist metadata selection also uses separate `/api/v1/artists/metadata/browse-page` and `/browse-count` endpoints. Browse selects matching artist IDs before loading membership counts, playlist names, artwork and provider profiles. The metadata page skips monthly listening history and still reads the requested listening sort total. Search, filter modes, ranges, freshness and result caps share one membership predicate across both surfaces. Each search word or group of Any filters builds one set of matching IDs, so the page and count can join to it without rescanning the same matches for each artist. Playlist count sorting counts distinct artist and playlist pairs before joining the totals. `artist-browse.integration.ts` and `artist-filter-performance.integration.ts` check these paths with disposable synthetic libraries.

The film collection directory follows the same split through `/api/v1/collections/browse-page` and `/browse-count`. Name search, film-only membership, ordering and the page limit are evaluated in SQL. The directory's hidden-by-default source column requests `includeSources=true` only when shown; provenance expansion is restricted to returned collections, never the entire directory or its count query. Arbitrary plugin source readers are not an indexed directory sort/filter field. Collection membership IDs travel with film rows so opening a collection requires no directory lookup.

On a disposable fixture of 20,000 synthetic tracks, the exact count for a required Album track list filter took about 123 ms, while the first page and its metadata took about 10 ms. On 50,000 synthetic subscription items, the original first page with a window count took about 22 ms. Executing the page and exact count independently took about 0.3 ms and 3.8 ms respectively. These are medians from five warm database measurements, excluding HTTP and browser rendering.

## Artist and album filtering

Artist freshness queries probe the latest relevant job through partial expression indexes on `scrape_job`. The artist task predicate and timestamp null ordering must match those indexes. Current profile state is read through its artist/provider key. Metadata hydration looks up only the displayed artists and requested providers; never join every historical job to every visible artist.

Artist scrobble ordering and ranges read the stored `artist.scrobble_count`. Counting linked scrobbles per request joined every scrobble to its credits and removed duplicates across the album and track links, which took seconds on a long listening history. `refreshArtistListeningTotals` recounts after links change: it groups scrobbles by scrobbled name and album link first, because every scrobble in a group has the same links, and writes only changed artists. The page's sparkline covers the whole listening history, so it reads every scrobble of the displayed artists, grouped by month in one statement that also reads the date of the earliest stored scrobble. That date steps through the listeners on the listener and time index and takes each one's first scrobble; a plain minimum over the table reads every scrobble. On a disposable fixture of 315,000 synthetic scrobbles that all belong to the displayed artists, the worst case, the date took about 3 ms instead of 26 to 80 ms, and the sparkline read about 600 ms against about 205 ms for the earlier twelve-month read. A page of artists with few scrobbles reads correspondingly few rows.

Album tag filtering and ordering calculate canonical artist tags and sparse release-tag fallback as sets. Exact playlist chips join indexed membership IDs. Tag hydration remains bounded to the returned media IDs. These paths share the same fallback and alias rules as displayed tags.

Multiword Album and Track searches match each word against artist tag labels before joining matching artists to media credits. An individual word can still match a different field from its neighbours. The performance suite covers two-word Tracks searches ordered by Artist, including a broad result, a cross-field match and a miss. For filtered first pages ordered by Artist, Album, Released or Duration, the query fetches the primary page with all boundary ties, then applies the release order. Artist ordering uses the first billed credit and switches from individual lookups to a join for large result sets. On the regression fixture, the broad two-word Artist search read about 67,000 shared blocks, down from 389,000. A selective six-row duration filter with the Artist sort read about 4,800 blocks, up from 670. Keep both workloads in the suite.

When an Album or Film spends most of its time loading page details, measure the bytes PostgreSQL sends as well as the statement count. Credits and playlists on lists and detail screens share small projections for the fields returned by the API. The API still returns the full public metadata for each media item and provider reference.

Autocomplete starts when search receives focus or text, rather than running a broad facet aggregation for every page mount. It retains debounce and request cancellation. Broad suggestions still count values across the matching library.

On disposable synthetic fixtures, the artist never-attempted page query fell from approximately 5.8 seconds to 33 milliseconds. Album tag ordering fell from approximately 2.2 seconds to 118 milliseconds, and a two-word album search fell from approximately 953 to 173 milliseconds. These are local database/service measurements, not production HTTP latency guarantees. The performance integration suites assert query results and indexed/bounded plans rather than fixed machine-specific timings.

Filtered artist bulk selection inserts matching IDs directly into an owner-bound, one-hour snapshot. It uses the Browse membership predicate and result cap without fetching profiles or all table pages. Dispatch reads that snapshot in bounded batches, rechecks freshness and active jobs, and preserves provider concurrency and cooldowns.

## Combined filters and large directories

An exact Artist tags chip resolves the requested tag, its visible descendants and the raw labels that can map to them. A GIN index finds matching profile snapshots by normalized label. Only the current snapshot for each artist and provider contributes credits. An explicit hidden tag still matches, and edits to aliases and parent tags take effect on the next read. Track pages load artist tags for their returned IDs together.

For filtered first pages ordered by plays in a selected period, narrow recording sets use indexed counts for their distinct linked names. Broad filters retain the aggregate over listening history. A page boundary can have thousands of tied recordings. The performance suite checks the number of rows rejected by join filters across all execution loops as well as logical reads, so repeated scans of cached rows still fail the budget.

For grouped lifetime play order, a library-wide page can read stored ranks and recording membership together. A page with text search or Genre chips and a listening filter can reuse the current visible membership. It computes the representative, play total and rank from the editions matching the filters. Playlist chips and dirty or incompatible generations use live grouping. A single zero-play rule can check each group against the distinct group keys played in the period. When investigating CPU spikes, check rejected join rows as well as logical reads on both the published and live paths.

The browser starts its automatic exact count after the first page for the current query settles. Rows render independently. When returning to a scrolled view with a known count, the browser fetches the visible pages first. It can render cached neighboring rows without immediately refreshing them. A grouped Tracks count with only listening filters reads both totals from one published generation. On a miss, one SQL statement shares the live membership between the filtered and unfiltered totals. Cloudflare runs the three scheduled database rebuilds in sequence. Compare their individual start and end times with slow foreground requests.

For early pages combining several listening presence or absence rules, the reader first checks a bounded range of stored ranks. A single rolling zero-play filter can also use this path. It samples 32 ranks before expanding its search. Sparse matches fall back to the full eligible set in the same snapshot, so the returned order and page boundaries remain exact. Deep jumps skip the probe. The budget suite covers the browser's 100-row page size and a date range with no matches.

On the first ungrouped Tracks page sorted by newest addition, a positive Artist tags filter checks Last.fm source visibility for candidate tracks. The same query can match a handful of tracks or most of the library. A synthetic fixture with 12,000 Last.fm source rows checks both extremes, including retained tracks and a date tie across the page boundary. PostgreSQL tests membership using the matching IDs and resolves release order at the boundary. For the broad fixture this eliminated 240 million rejected join comparisons and reduced database execution from about 6.7 seconds to 25–27 ms on PostgreSQL 17 and 18.

Global Track visibility first identifies Last.fm placeholders that could be hidden as duplicates. When few qualify, the query looks up each eligible name through the exact-match index. For larger sets it joins the eligible names to exact links before checking whether their peers are playable. Benchmark this through a Browse page as well as the visibility query on its own. The page limit and sort can change PostgreSQL's join strategy.

A standalone zero-play or at-least-one-play rule uses an existence check. Multiple rules and sorts that need exact counts share one aggregate over the listening history. Grouped Tracks use indexed normalized titles for small candidate sets and check every visible peer of those titles before admitting a recording group. A page resolves the release order of every group tied at its primary sort boundary. Broad grouped reads still process the matching recordings.

On a disposable PostgreSQL fixture with 20,000 tracks, 9,000 current artist profiles and 240,000 recent scrobbles, a required playlist, artist tag and rolling year with zero plays selected 32 tracks. Median database timings from three warm executions follow.

| Query                  | Before | After |
| ---------------------- | -----: | ----: |
| Track page IDs         | 331 ms | 16 ms |
| Exact track count      | 231 ms | 16 ms |
| Grouped track page IDs | 330 ms | 27 ms |
| Exact grouped count    | 306 ms | 27 ms |

The table measures database execution for IDs and counts. Loading full track details separately took 11 ms for 50 tracks (previously 96 ms) and 33 ms for 250 tracks (previously 1.1 seconds), using the median of five warm service calls. HTTP and browser rendering add to those times. The unfiltered grouped play-count measurements below use a separate fixture.

Jobs counts group matching batch IDs without sorting or loading individual job details. The page limits individual jobs before combining them with batch summaries. Subscription and Mixes compatibility pages count narrow rows and load page details within the same SQL statement, including when a page lies beyond the last match. Source directories count stored items through each source's indexed membership. In separate synthetic fixtures, the Jobs first page took 15 ms for 300,000 jobs (previously 229 ms), and a subscription page with its exact total took 32 ms for 250,000 items (previously 306 ms). These are medians of five warm database measurements.

## Sorts, ranges and autocomplete

Titles are required, so descending title order can scan the title index backwards. On 20,000 synthetic tracks the first 50 IDs took 0.8 ms, down from 192 ms. A one-day Added range on 65,000 tracks counted 25 matches in 0.13 ms, down from 26 ms. Film and Album Released ranges also use the stored timestamp for whole-millisecond bounds. Fractional bounds retain their exact precision. When a result cap is the only filter, one count supplies both the displayed total and the uncapped total.

Tracks and Albums resolve tag labels and their visible ancestors before joining media memberships. On 60,000 tracks, 6,000 albums and 60,000 current artist profiles, a one-character autocomplete request fell from 2.02 to 1.22 seconds for Tracks and from 493 to 328 ms for Albums. A selective search took 333 ms and 113 ms respectively. Albums and custom Track scopes still aggregate live memberships. Default Track autocomplete now reads the stored vocabulary described below.

For genre filters, an artist tag can qualify a track when its album has too few distinct visible release tags, including when the track has no album. Browse computes the set of albums meeting that threshold once per filter. On 20,000 synthetic tracks, a grouped page sorted by lifetime plays used 972 shared buffer accesses for an absent genre, down from 82,242. A broad genre present on both releases and artists used 9,661, down from 49,559. The regression suite checks the missing-genre case with a listening filter and verifies artist fallback for a track without an album.

Tags filters on Tracks read tags at a location: Auto, or the track's own tags, its album's and its artists' ([Track tags](requirements/track-tags.md#stage-3-filtering-by-tag-location)). Each location is one hashed set of track IDs, with the tag set resolved once inside it and read as `= any(array(…))`, tested on the table the sort order walks: `media_item` on a Title page, `library_track` otherwise. The album Tags filter used to test album IDs on `library_track`; on a Title page PostgreSQL then nested-looped every walked track against the materialised tracks. On 20,000 synthetic tracks the first Title page for a tag on half the tracks took 9.7 seconds and rejected 149 million join rows; as a set of track IDs on `media_item` it rejects six and reads a third of the blocks. On Added pages the Last.fm visibility test did the same until Tags filters took the first-Added-page path that Track tags filters take (about a million rejected rows to six). Whether Sonovault uses a tag is one probe of the partial index for the statement; as `tag_id in (select …)` the planner scanned all of `track_tag` with a nested loop. Counting Tags suggestions for a combination of levels live took 2.0 to 2.7 seconds on production with nothing typed, so the stored Tracks vocabulary holds each combination too: a group of tracks with the same album and artists that has the value at a ticked album or artist level counts all its tracks, otherwise only those carrying the value themselves. The build took 1.7 seconds on the suite fixture, against 1.1 before.

The Provider filter on Tracks is one hashed set of the track IDs a provider knows, read from `provider_reference` without an index on `provider`, and placed as the Tags filters are: on `media_item` for a Title page, on `library_track` otherwise, with Added pages on the first-Added-page path. On 20,000 synthetic tracks with an ISRC on each, a TIDAL ID on two in three and a Sonovault match on every tenth, the first Added page for `tidal` read 146,553 blocks in 311 ms and rejected 1.1 million join rows before it took that path, and 13,830 blocks in 11 ms with none after. The first Title page reads 53,028 blocks (69 ms) for `tidal` and 12,220 (22 ms) for `sonovault`; excluding them reads 26,429 and 67,237 blocks, and an excluding Added page reads 3,333. Sorting by provider costs what sorting by Duration costs. These are budgets in `track-query-budgets.performance.ts`.

Subscription and Mix autocomplete count scalar values once per item and collapse repeated array labels within each item on broad searches. On a synthetic fixture with 160,000 subscription and mix items, empty autocomplete took 180 ms for Subscriptions and 256 ms for Mixes, down from 584 ms and 683 ms. Artist suggestions collapse repeated profile labels and playlist memberships before counting.

### Grouped play counts

Unfiltered grouped Tracks sorted by lifetime scrobbles share two stored recording orders, one per direction. Each order includes the release tie-breaks. A page, an exact total and an arbitrary position can read the same published ranks. Filtered groups and period-specific listening sorts continue to use their own query predicates.

The first request for a slow order can spend up to 3.5 seconds attempting to publish before it reads the exact live result. Subsequent requests skip that attempt. The five-minute cache maintenance task gives previously requested, stale orders up to 60 seconds to publish. An active lease prevents overlapping publications.

On a disposable fixture of 64,000 tracks and 252,000 scrobbles, the first descending page took 2.08 seconds including publication, compared with 2.04 seconds for a live read. Further descending pages took 2.2 ms, down from 1.87 seconds. Ascending pages took 1.4 ms, five arbitrary positions took 1.7 ms and a total took 0.7 ms. These timings measure the service before track detail hydration.

### Tracks autocomplete

Default Tracks autocomplete stores the distinct values and exact counts for each of its ten text fields, ranked by count and display value. Suggestions on focus can read the first ranks for each field. Typed suggestions retain exact-value priority, multiword substring matching and per-field limits. A cold selective request can still search indexed live rows. A broad request can build the vocabulary for subsequent searches from any Worker. If a build exceeds the five-second foreground budget, later requests search live while the existing five-minute maintenance check rebuilds it with a 60-second budget. Each check skips unused and current vocabularies. Newly committed edits remain visible during that interval.

The live fallback groups visible tracks by album and credited artists before expanding tags. Each distinct label contributes the size of its group to the result. The tag-rich regression fixture covers aliases, album and artist overlap, and broad and selective searches. On PostgreSQL 18 its one-character search fell from 1,848 to 350 ms and eliminated temporary writes with 16 MB of work memory.

On 60,000 synthetic tracks, a fresh application process served empty suggestions in 3 ms with a current vocabulary. One-character, common-word and selective searches took 23 ms, 16 ms and 13 ms of database time, down from 1,143 ms, 629 ms and 373 ms on the same fixture. Building on the first request took 1.22 seconds, compared with 1.18 seconds live. The ranked values and index occupied about 9 MB on this fixture.

Album autocomplete uses its own ranked vocabulary. It counts editions and excludes archived albums by default. Suggestions with Include archived use the live query. A Tags location counts the Tags field live and reads the other fields from the vocabulary. The live playlist aggregate deduplicates album and playlist-name pairs before counting, since an album can be in a playlist directly and through several tracks.

Stored results use transactionally maintained invalidation markers. Relevant source writes mark the cache dirty in the same transaction. Readers use a single snapshot to check freshness and select results. A rebuild publishes atomically and can clear only the committed markers it observed. Reads during rebuilds and cooldowns can use the live query.

### Deep Track pages

Track page jumps and position requests preserve their absolute ranks, including ties that cross either page boundary. For deep sorts by Title, Added, Artist, Album, Playlist, tags, Released, Duration or ascending lifetime scrobbles, PostgreSQL finds the range of primary sort keys containing the requested positions before looking up release credits and track numbers. For a selected listening period, the count aggregate keeps linked tracks that have zero plays in the window. This lets the planner estimate the number of links before joining the counts to Tracks. On 20,000 tracks and 240,000 scrobbles, a two-month play-count sort at page 390 fell from 3.65 seconds to 123 ms.

On the 20,000-track fixture used for the combined-filter measurements, a title jump to page 390 at 50 tracks per page took 86 ms, down from 239 ms. The first page took about 1 ms both ways. On a separate 20,000-track fixture, a deep Released page fell from 101 ms to 37 ms and Duration fell from 99 ms to 28 ms. Early pages keep the direct ordered limit. Large tied groups and the number of primary keys preceding the page still affect the cost. Rolling listening windows move between requests, so an exact total with a rolling filter bypasses the snapshot cache. Stable date ranges and unfiltered totals retain snapshot validation.

## Verification

The browse-search and query-indexes integration tests create disposable databases and synthetic libraries. They cover query results, substring escaping, cross-field word matching and PostgreSQL query plans. They do not read or scrape a real library. Run them from the workspace root:

```sh
corepack pnpm --filter @repo/server exec vitest run --config vitest.integration.config.ts integration/browse-search.integration.ts integration/query-indexes.integration.ts
```

On a local synthetic fixture of 20,000 tracks linked to 1,000 albums, a selective title search plus autocomplete took approximately 8.5 seconds before these changes and 83 milliseconds afterwards. This measures the service calls with fixture setup excluded, not browser or network latency. Plan assertions check that a selective search reads album positions only for matching tracks and that default Track ordering can use its Added-date index. Tests do not depend on a machine-specific millisecond threshold.

The live fallback for broad autocomplete on that fixture took approximately 0.5–0.6 seconds for empty input, one character and match-status labels. Those requests still count values across the library; the selective-search improvement is not a latency guarantee for every filter or library size.

## Upgrading

Migration `0028_library_search_indexes` enables `pg_trgm` and builds the search and lookup indexes. The database role needs permission to install this extension. It uses the existing transactional migration runner; index construction can block writes while it runs. Follow the normal [upgrade procedure](getting-started.md#upgrading-and-backing-up): back up, stop application writers, apply migrations, then start the updated application. No provider refresh or library reimport is needed.

Migrations `0031_artist_filter_indexes_and_selection` and `0032_artist_browse_name_index` add the artist job lookup indexes, name ordering index and temporary selection tables. Existing tables can have those three indexes built with `CREATE INDEX CONCURRENTLY` before applying the migrations; use the exact definitions, verify `pg_index.indisvalid`, and run each concurrent statement outside a transaction. The migration statements use `IF NOT EXISTS` to accept these prebuilt indexes. Do not treat an existing invalid or differently defined index as ready. Otherwise follow the normal stopped-writer migration procedure. No re-scrape is required.

Migration `0034_artist_scrobble_count` adds `artist.scrobble_count`, fills it from the stored scrobble links and builds its ordering index. It needs no re-scrape or relink.

Migration `0041_browse_query_indexes` builds the normalized artist-profile tag index and the media-type/normalized-title index, then updates planner statistics. Follow the standard upgrade procedure before starting this version. Existing snapshots and tracks supply all indexed data.

Migration `0050_grouped_recording_order_members` adds a derived table for tracks in multi-edition recordings and an index on the recording representative. Singletons use their own track ID. The maintenance transaction publishes membership and both lifetime ranks together. The new reader accepts only a clean generation built by its own database role and algorithm version. If the runtime uses a separate database role, grant the same read and rebuild privileges on the new table that the role has on the existing rank table. Rebuild through the existing recording-order maintenance operation after upgrading; library records require no conversion.

Migration `0052_scope_recording_source_invalidation` compares the affected artist, track and listening-event rows before marking a cache dirty. Replaying the same imported plays or inserting already-known artists leaves a current generation available to readers. Changes to grouping, ordering and listening history still invalidate it. The migration replaces triggers and needs no backfill.

Migration `0053_artist_mix_exact_names` indexes the names of billed artists and subscribed shows. Artist Overview uses those exact names to find candidate mixes before counting and sorting. The same mix can match both a billed artist and a show title and still appears once. For a busy installation, create the migration's function first, build its two indexes with `CREATE INDEX CONCURRENTLY`, verify the definitions and validity, and then run the journaled migration. The PostgreSQL 17 and 18 performance jobs exercise a common search word that appears in many broadcasts and matches no artist name exactly.

Migrations `0042_grouped_recording_browse_order` and `0043_track_facet_vocabulary` create the derived tables and their invalidation triggers. They populate on demand. A separate reader role can continue to query the live data. A runtime role that builds caches needs read access to the derived tables, insert and delete on the rank and value tables, insert and update on the state tables, and delete and update on the invalidation tables. The source write triggers run with the migration owner's privileges. Existing library data supplies both caches.

Migration `0044` stores the decision to rebuild a slow autocomplete vocabulary during maintenance across requests and Worker restarts.

Migration `0070_album_facet_vocabulary` adds the Albums vocabulary, its state, and its invalidation triggers. It grants the derived-table operations to the runtime role when that role exists. The vocabulary is populated on demand and maintained independently from Tracks.

Migration `0045` adds a B-tree for listening presence checks by track name, artist name and time. Retain the shorter name index for other access patterns. Migration `0046` narrows invalidation of the two stored Track browse caches. Both use stored data and require no reimport. On a busy database, build the `0045` index concurrently ahead of cutover using the migration's exact key order. Verify its definition and validity before applying the journaled migration.

Migration `0047` limits Track vocabulary invalidation from artist enrichment to changes that can affect tag labels. Saving history and replacing a current profile with the same normalized tags preserve the vocabulary. The publication check locks the affected snapshots while comparing tag sets.

Migration `0048` stores the background-only refresh decision for slow grouped recording orders. Existing published ranks remain readable.

Migration `0056` rebuilds the stored recording order triggers so stored versions invalidate it, and `0057` adds the possible-duplicates groups' invalidation triggers and redefines `mark_browse_cache_dirty()`. The scheduled maintenance of the Worker and of the Node job worker rebuilds the groups. Every statement of the rebuild is a round trip from the scheduled Worker, which can run far from the database, so the rebuild reads and writes in batches of 2,000 rows and reads the merge plans of all new groups together (`readTrackMergeOutlines`: three statements for up to 2,000 tracks) instead of four statements for each group. One rebuild plans at most 2,000 new groups and the next runs plan the rest. On a library of 81,000 tracks with 5,600 groups a rebuild is a few dozen statements; planning each group by itself was over 22,000. The rebuild has no workload in the performance suite yet. See [releasing the merge stages](library-merge-handover.md#releasing).

### Trigger functions and transition tables

A statement written directly in a PL/pgSQL trigger function is planned once per connection and the plan is kept, whatever the transition tables hold on later writes. In `0057`, `drop_track_duplicate_groups()` joined `old_rows` to `new_rows` this way. Planned for a one-row update, the join compared every old row with every new row of a later bulk update on the same connection: 12,000 rows took over twenty seconds instead of a fraction of one. Migration `0059` runs the function's statements with `EXECUTE`, which plans each for the rows of its own write, as `mark_browse_cache_dirty()` does.

A trigger function that joins transition tables to each other must use `EXECUTE`. `forget_match_rejections()` reads one transition table against a primary key and was measured unaffected. The performance suite runs a bulk track update after a one-row update on one connection under a five-second limit.
