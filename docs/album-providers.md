# Album provider contracts

The current album adapters validate responses at the provider boundary and return shared media contracts. Tests use synthetic responses through mocked requests. Private integrations are loaded separately through the plugin SDK.

MusicBrainz artist countries may be absent or null. Unknown countries do not
prevent an otherwise valid release group from being matched or imported.

## Supported adapters

| Provider    | Behavior                                                                                                                                                                                                                             |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| MusicBrainz | Uses an owned release-group ID first, then bounded barcode/name searches. Retains relations without changing another provider's identifiers.                                                                                         |
| Last.fm     | Looks up the album by album MBID, corrected URL, or canonical names. Ranked album tags are opt-in. Release-group IDs are not album MBIDs.                                                                                            |
| Discogs     | Uses an owned corrected ID or bounded native barcode/master/release searches. A master lookup fetches its main release only.                                                                                                         |
| Spotify     | Supports album metadata and the separately authorized [saved-album import](spotify-album-imports.md). Audio-feature acquisition is excluded.                                                                                         |
| Serply      | Looks up indexed Rate Your Music results. Search-derived ratings can lag the source.                                                                                                                                                 |
| TIDAL       | Matches by the Spotify album's UPC or a stored TIDAL ID and aligns its tracks; tracks match by ISRC. Catalogue data only; see [TIDAL](#tidal).                                                                                       |
| Sonovault   | Paid lookup service. Looks up library tracks by Spotify track ID or ISRC, or by artist and title for review, and albums through their tracks' records, and stores the IDs it reports on other services; see [Sonovault](#sonovault). |

Google Custom Search is retired. Historical ratings and source links remain importable under the existing provider ID; see [retirement behavior](google-search-retirement.md). CSV and legacy JSON files use the current [import workflows](importing.md). Archived scrapers, cleaners, playlist-sync helpers and prototypes are no longer included.

## Request safety

| Provider    | Concurrency / minimum spacing | Lookup requests per album before transient retries                                   |
| ----------- | ----------------------------- | ------------------------------------------------------------------------------------ |
| MusicBrainz | 1 / 1000 ms                   | 1 direct; 2 name or barcode; 3 barcode miss then name                                |
| Last.fm     | 1 / 200 ms                    | 1 normally; 2 with `options.includeTopTags: true`                                    |
| Discogs     | 1 / 1050 ms                   | 1 release; 2 master; at most 4 with searches                                         |
| TIDAL       | 1 / 1500 ms                   | 1 per 20 album tracks; 1 per track match or similar read                             |
| Sonovault   | 12 jobs / 1100 ms or more     | 1 per 100 tracks (bulk call); 1 credit per track; 1 per track, then 1 to 6 per album |

Every HTTP request, including searches, uses `context.request`. There are no client libraries, direct fetches, hidden retries, pagination walks, quota-discovery calls, or network activity on module import. The persistent server gate owns spacing, timeouts, cooldowns and shared budgets. Runtime account access is not proven by these offline tests. The MusicBrainz, Last.fm and Discogs plugins do not claim a connection-test hook; no credentials are tested on import. The separate [Last.fm scrobble sync](lastfm-scrobbles.md) runs as account-level Last.fm jobs outside the plugin; it pages `user.getRecentTracks` through the same Last.fm gate and repeats a page after a temporary failure. Last.fm sets `errorBackoffMs: 5000` and `failureCooldownMs: 0`: an HTTP 400 or 5xx delays the next request by five seconds without a provider cooldown, for album jobs as well.

Serial metadata jobs can make up to three attempts for a bodyless GET returning HTTP 502, 503 or 504. The shared gate records every request and the job logs each retry, with five- and ten-second minimum backoffs and any longer `Retry-After`. This does not extend adapter search windows. Concurrent providers, account task jobs, writes, timeouts, authentication errors and rate limits do not gain this retry behavior. See [job worker](job-worker.md) for the retry window and repeated-failure threshold.

An existing owned reference is validated before any search. Invalid IDs fail immediately, rather than silently searching for a different album. Search windows are at most five MusicBrainz/Discogs candidates. Ambiguous matches or responses reporting more candidates than the bounded window require a direct corrected ID and are not marked benign. Discogs keeps these cases as failed jobs for review without counting them toward its provider safety stop. Validated searches with no matching item throw `ProviderItemNotFoundError`; malformed bodies, HTTP failures and access denial are not benign misses. Transport/gateway errors retain their type and retry time. Last.fm error 29 uses `ProviderRequestError('rate-limit')`, without retries, with at least a 60-second retry time extended by Retry-After. Existing shared request-gate quota classification remains unchanged by Google retirement; it no longer implies an active Google adapter.

## TIDAL

`tidal` reads the catalogue at `https://openapi.tidal.com/v2` (JSON:API, `Accept: application/vnd.api+json`). Configure its client ID and secret in Providers → TIDAL → Settings, or with `TIDAL_CLIENT_ID` and `TIDAL_CLIENT_SECRET`; an optional country (default `AU`) sets the catalogue it answers for. The server requests a client-credentials token from `https://auth.tidal.com/v1/oauth2/token` and keeps it in memory until five minutes before it expires (tokens last four hours). Tokens never reach the browser, and token requests are not kept in request history. Nothing plays through TIDAL: third-party playback is limited to previews.

TIDAL matches and similar reads are not queued: each runs in the request that asks for it and returns its result there ([jobs run in the request](job-worker.md#jobs-run-in-the-request)). Its job row is kept as the record that holds the requests and responses. Requests still go through the request gate one at a time, 1.5 seconds apart, shared with any other TIDAL work. A request waits at most 10 seconds for its slot. TIDAL publishes no limits and sends no rate-limit headers; a 429 cools the provider down until its `Retry-After`, or for five minutes without one. A cooldown or busy slot answers "TIDAL is rate limited. Try again in N seconds." Every response is stored with its record and validated before use.

**Albums.** A TIDAL album match, from the album's Sources, metadata selection or the Similar tab, reads `GET /albums?filter[barcodeId]=<UPC>&include=items` with the UPC of the album's Spotify album, or `filter[id]` with a TIDAL album ID already stored for it. It never searches by name. No result is a not-found; a barcode TIDAL reports differently, or a rejected album, is not a match; two albums for one UPC need the TIDAL album ID set. The first response holds up to 20 tracks; longer albums read further pages of `/albums/<id>/relationships/items` by cursor, up to 500 tracks. The match stores a `tidal` `album` reference and a TIDAL link. The track list is then aligned to the library album's tracks: by position when both lists have the same length and the durations agree within three seconds or the titles match, otherwise by a unique title with a duration within three seconds. Each aligned library track gains a `tidal` `track` reference (TIDAL track ID, link, version, duration, popularity, and BPM and key when TIDAL returns them, which it did not for this app in November 2026) and its ISRC as a `tidal` `isrc` reference. A track without a primary ISRC takes TIDAL's when the alignment agreed on duration. A later album match replaces that album's alignment. Like the other providers, TIDAL supplies the library track list only until Spotify supplies one.

**Tracks.** A TIDAL track match is a task (`tidal-track-match`) for one library track with an ISRC, run in the request; a selection in Tracks → Matches sends 10 tracks a request, one after another, and stops at a rate limit. It reads `GET /tracks?filter[isrc]=<ISRC>&include=albums`. When several TIDAL tracks carry the ISRC (the same recording on a single, an EP, an album and compilations), the match keeps those on a release whose barcode equals the UPC of a library album the track is on, then those whose duration is within two seconds, then those whose version agrees with the library title, then those that can be streamed. One left is stored as the track's `tidal` `track` reference with its ISRC. Several left are kept with the record for review in Tracks → Matches and the track's Sources, where choosing one stores it. None is a not-found.

One request can carry 20 barcodes or 20 ISRCs, but a job is one item, so jobs send one each.

**Similar.** The Similar tab of a matched album or track reads TIDAL's first page of 20 similar items in the request, as the TIDAL task `tidal-similar` for that one item: `GET /albums/<id>/relationships/similarAlbums` or `GET /tracks/<id>/relationships/similarTracks`, with `include=similarAlbums,similarAlbums.artists` (or the track form) so titles, artists, version and the barcode or ISRC arrive in the same response. The suggestions are kept in TIDAL's order in `tidal_similar`, one row per library item, replaced by the next read; the raw response stays with the record. Opening the tab reads it once when the item has none, after the page has loaded; Read again reads it again. An item not yet matched on TIDAL offers Match on TIDAL, which runs the album or track match in the request; the tab then reads its similar items. A track with no TIDAL match but a verified Sonovault record is read with that record's TIDAL ID instead, with no match first; if TIDAL answers 404 for it, the same request matches the track and reads it once (SIMILAR-05). The count line says which ID the list was read with.

A suggestion is in the library when its ISRC is an `isrc` reference of a library track, or its barcode, leading zeros ignored, is a `upc` reference of a library album. This is worked out when the tab is read, so items added later count. For the rest of a track's suggestions, the TIDAL read itself sends one Sonovault bulk resolve of their ISRCs (SONO-26), through Sonovault's request gate, waiting at most 10 seconds for a slot; its response is stored with the read's job under provider `sonovault`. A record with a Spotify link whose title and duration agree with TIDAL's (as in Sonovault verification) is stored in `spotify_code_lookup` with `source` `sonovault`, its `response_id` and fetch time; the read then queues the Spotify lookup for the ISRCs it did not map. When Sonovault cannot be used, and for albums, the TIDAL read queues the Spotify task job (`spotify-similar-lookup`) for the same item directly, with at most 20 codes: one `isrc:` or `upc:` search each through the Spotify request gate and Spotify's track-search access (a market, or the signed-in Spotify account). A UPC is searched as TIDAL wrote it. Of several Spotify tracks for one ISRC it keeps one that is already a library track, then the earliest release that is not a compilation, then Spotify's first. Each result, or a miss, is stored at once in `spotify_code_lookup` by code with the time of the search, and is reused for every item that suggests it; a miss is searched again after 30 days. A Spotify ID that belongs to a library item counts as in the library. When Spotify cannot search (no market and no connected account, a cooldown), the suggestions stay "Not looked up on Spotify" and the TIDAL record's message says why. Nothing is looked up library-wide, and nothing plays until Play or Add to queue is pressed.

## Sonovault

`sonovault` is a paid lookup service that, given a track's Spotify track ID or ISRC, returns the same recording's IDs on other services. It fills identifiers only: nothing plays through it, and it has no similar or recommended tracks, so TIDAL and Last.fm remain the sources of related music. See the [Sonovault requirements](requirements/sonovault.md) for which stages are built; this section covers track lookups, tracks with no identifier and album lookups. It is listed among the album and track providers; album lookups are queued from an album's Sources or the API, not from album metadata selection.

**Settings.** The API key is a provider secret (`SONOVAULT_API_KEY`, sent in the `x-api-key` header) set in Providers → Sonovault → Settings or in the environment; it never reaches the browser. Optional settings are requests per minute (default 60), monthly credits (default 50,000) and a credit reserve (default 2,000).

**Rate limits and credits.** Up to twelve Sonovault jobs run at once (bulk track lookups before album jobs: `options.dispatchPriority`; a similar-track lookup is sent in the TIDAL read instead of queued), and every request goes through the shared request gate, which starts requests at least 1.1 seconds apart across all of them, or further apart when requests per minute is lower: never more than 60 in a minute. Sonovault is paced from reservations (`paceFromReservation`): each reservation sets the next one 1.1 seconds later and requests may overlap, without a provider-wide lock while one starts; a request must start within the 4-second dispatch window, so any 60 seconds hold at most 59 starts. A 429 cools the provider down for the seconds in `RateLimit-Reset` (the SDK option `ietfRateLimitHeaders`), and a response with `RateLimit-Remaining: 0` holds further requests until that reset. Credits are charged per input line, not per request. Before each request the job compares its line count with the credits the latest stored response reported in the same UTC calendar month, or with the monthly credits setting when there is none; a report from an earlier month counts as the full monthly credits. When the reserve would be crossed, the job stops without a request and its message says so. A `skipped_no_credits` line is left un-looked-up and is not recorded as a miss.

**Lookups.** The task job `sonovault-track-lookup` sends one bulk request (`POST /v1/tracks/resolve`) for up to 100 library tracks of one input type: by Spotify track ID where the track has one, otherwise by ISRC. It is queued from Tracks → Jobs → Metadata (the selection action, the Sonovault column and the freshness filter) or from a track's Sources. Check one track, then one request of 100, before a larger run. A track found nothing for is recorded with its date in `sonovault_track_lookup` and not looked up again for 30 days.

**What it stores.** Every request and response is stored with its job, like other providers' history, and validated with a schema before use. Each matched track's own record is also kept on its `sonovault_track_lookup` row (`record`: its result line with links, or its entry on an album's release and the release ID), so it outlives its job and response and is never requested again before a refresh; `corepack pnpm --filter @repo/server backfill:sonovault-track-records [--dry-run | --apply]` fills rows stored before that from their responses without requests. Each matched track gains `provider_reference` rows with provider `sonovault`: `sonovault-track` (the Sonovault track ID, with the record's ISRC, title and duration in `metadata`) and, for each link Sonovault returned, `spotify-track`, `applemusic-track`, `tidal-track`, `beatport-track`, `musicbrainz-recording`, `discogs-release-track` (release ID and track position) and `youtube-video`. Every reference's `metadata` holds `url`, `verified`, `fetchedAt`, `responseId` (the stored response), `jobId` and `inputType`. Only rows with provider `sonovault` are written: other providers' references and the library track's Spotify ID are never changed, and the `spotify-track` reference is kept as a reference only. Later stages read tempo, key, genre and releases from the stored response by `responseId`, not from the references.

**Verification.** A record is verified when its duration is within five seconds of the library track's where both are known, and the titles are equal after `trackVersionKey` (case, punctuation and version-text notation ignored). The references of a failing record are stored marked unverified and are listed in track details, but other features do not use them. An unverified record's ISRC is not written as an `isrc` reference, because TIDAL matching, the Similar tab and other features read those; it stays on the `sonovault-track` reference and is listed in track details. A verified record's ISRC is stored as a `sonovault` `isrc` reference. A verified lookup by Spotify ID fills an empty `library_track.isrc`, and `sonovault_track_lookup.primary_isrc` marks the value as Sonovault's while it equals the primary ISRC. An ISRC that a Spotify track search acceptance or ISRC recovery later reports replaces it, and playlist imports already replace the primary ISRC with Spotify's.

**Tracks with no identifier.** A library track with neither a Spotify ID nor an ISRC is looked up by artist and title (`track_name` lines in the same bulk call and the same `sonovault-track-lookup` task, with `inputType: track_name`): its first credited artist and its title, without a Last.fm track-number prefix. The search ignores version text, so a result is stored as a candidate in `sonovault_track_candidate` with the response line it came from, and gives the track nothing by itself. A candidate is accepted automatically only when the artists are equal, the titles are equal under `trackVersionKey` (version text included) and the durations agree within five seconds; a track with no stored duration is never accepted automatically. Every other candidate waits in Tracks → Matches. An accepted candidate gives the track the references and `sonovault` ISRC reference described above, marked verified, with `inputType: track_name`; it does not fill the primary ISRC (SONO-07). When the candidate links a Spotify track and the track still needs a Spotify match, a Spotify track search job reads that one track (`GET /v1/tracks/{id}`, stored with the job) and takes its Spotify ID through the Spotify search acceptance: the automatic rules for an automatic acceptance, the owner's acceptance path otherwise, so Spotify ID uniqueness and duplicate groups are handled as for a search match. A conflict leaves the Spotify result for review in Sources. When the match moves a Last.fm track's names to a Spotify recording, that recording gets the Sonovault references. A rejected candidate is not offered again, and a track with a candidate is not looked up by artist and title again; a miss is retried after 30 days. To queue the most scrobbled tracks with no identifier: `corepack pnpm --filter @repo/server queue:sonovault-track-names --limit <n>` counts them, and `--apply` (with `--confirm-broad-run` above five) queues them 100 to a job.

**Refresh and removal.** Sonovault's terms require stored results to be refreshed within 12 months and removed within 30 days of the subscription ending. Providers → Sonovault → Settings shows what is stored and the credits last reported. Refresh queues lookups for matched records older than 11 months, and album lookups for confirmed albums older than 11 months (track records read from a release are refreshed with their album), and deletes Similar-tab Spotify matches from Sonovault older than that, which are looked up again on the next similar read. Remove (`POST /api/v1/sonovault/remove`) does the following in one transaction: it clears the primary ISRCs Sonovault gave, deletes every `sonovault` reference, track and album lookup row and candidate, including `spotify_code_lookup` rows with `source` `sonovault` (counted with the lookups), and deletes every stored Sonovault response. Jobs keep their counts and messages.

**Albums.** The task job `sonovault-album-lookup` looks up one library album. Sonovault cannot look a release up by UPC or by a service's album ID, so it starts from the album's tracks. They are looked up first by the track lookup, 100 to a request, which gives each its own record. The album job reads the releases on all of the album's stored track records (from those lookups' stored responses, with no request of its own), ranks them by how many of its tracks list each, and fetches at most five from the top (`GET /v1/releases/{id}`, one credit each) until one is confirmed. An album whose tracks can still be looked up waits: its job records nothing and it stays due. A release is confirmed only by an identifier: an edition holding the album's Spotify album ID, a barcode equal to the album's Spotify UPC with leading zeros ignored (on an edition or as the release's digital UPC), or a MusicBrainz release group equal to the album's. A title never confirms one. The confirmed release is read again in the numbering of the edition that matched (`?edition=`, one credit; the Spotify edition first, then the barcode's, then the MusicBrainz edition closest in length), because a Sonovault release merges every edition and lists tracks with no position. Its tracks with a disc and track number are aligned to the library album's tracks by position, duration and title with the same alignment as TIDAL albums (`alignProviderAlbumTracks`). Each aligned track is written by the track lookup's own writer with input type `release`: a `sonovault-track` reference with `verified`, the ISRC of a verified record as an `isrc` reference (source `sonovault-album-lookup`), and the primary ISRC when the track had none and the alignment agreed on duration. Release tracks carry no service links, so aligned tracks gain no Spotify, TIDAL or other links. A track that has its own lookup keeps it. An album job therefore costs one or two credits, and at most six.

The album gains `sonovault` references from the release (SONO-21): `sonovault-release` (with what confirmed it, the matched edition and its label and catalogue number in `metadata`), `digital-upc`, and each edition's `discogs-release`, `discogs-master`, `musicbrainz-release`, `musicbrainz-release-group`, `beatport-release` and `applemusic-album`. Each has `url`, `fetchedAt`, `responseId`, `jobId`, `editionId` and `matchedEdition`; the types are Sonovault's own, so Discogs, MusicBrainz and TIDAL never read them as their matches. `sonovault_album_lookup` keeps the album's result: confirmed, or not found with its reason (no track to ask about, track not on Sonovault, no release on its record, or no candidate confirmed), the release and edition, the tracks aligned and the credits used. An album not found is not looked up again for 30 days. Before an album job the credits left must cover six credits above the reserve; release fetches report no credits, so the job records the last report less the releases it fetched.

`corepack pnpm --filter @repo/server queue:sonovault-albums` counts the library albums with a Spotify album ID by their album lookup (due, queued or running, confirmed, not found in the last 30 days) and the credits last reported, and changes nothing. `--album <id>` queues one album; `--queue <n>` queues the next `n` due albums (look up their tracks first) (more than 20 needs `--confirm-broad-run`). It prints counts and the batch ID only. Check one album, then about 20, before the rest, and watch the credits between batches: they are spent as the jobs run.

**Match review (SONO-22).** When a confirmed release's Discogs master or MusicBrainz release group differs from the album's own, or the album has no Discogs or MusicBrainz match, the album's Sources list it under Sonovault → Match review with both values, and Providers → Sonovault lists every such album. Sonovault's ID is then a stored candidate in that provider's row (Discogs or MusicBrainz → Find match), beside the provider's own candidates; choosing it saves and refreshes as any Find match choice does. An ID marked incorrect for the album is not offered. Nothing changes until a candidate is chosen.

**Routes.** Under `/api/v1/sonovault`: `POST /tracks/lookup`, `POST /tracks/lookup/status`, `GET /tracks/lookup/{trackId}`, `POST /albums/lookup`, `GET /albums/lookup/{albumId}`, `GET /albums/review`, `GET /albums/summary`, `GET /summary`, `POST /refresh` and `POST /remove`; for candidates, `POST /tracks/candidates/lookup`, `POST /tracks/candidates/status`, `GET /tracks/candidates/{trackId}` and `POST /tracks/candidates/{trackId}/accept` or `/reject` with the `sonovaultTrackId`.

Tests use invented responses; real Sonovault responses are never committed, published or passed to another service.

## Provider Workspace

Providers lists every integration in one table with a Library filter, and each provider has its own page (`/providers/<providerId>`). **Overview** contains job figures, request history, past error reviews and cooldown clears. **Jobs** is the shared jobs table for that provider. **Settings** groups credential fields, configuration status, environment fallbacks and supported remote checks with editable request budgets, effective request limits, lookup rules and integration details. Clear cooldown sits in the table's row actions and in the provider page's waiting notice. Switching tabs or providers only reads stored configuration and history; saving credentials, changing budgets, checking credentials and clearing cooldowns remain explicit actions.

## Integration Contract

`MediaPluginScrapeContext.media` supplies optional `{ title, artists, releaseDate? }`. Name lookup requires a nonblank title and artist; a direct reference does not require names. `supportsNameLookup: true` permits queue eligibility by names without manufacturing an ID. These are parent-owned SDK/server contracts.

All persisted namespaces are preserved: `musicbrainz:release-group`, `lastfm:mbid`, `discogs:master` / `discogs:release`, and the separate Spotify adapter's `spotify:album` / `upc`. The server annotates input references with `metadata.sourceProvider`; plugins consume only their own IDs. UPC/EAN is the sole cross-provider numeric identifier accepted here (8-14 digits). The latest manual Discogs selection is shared by master and release lookup. Both kinds of selection remain in history. Rejecting the latest selection leaves earlier selections in history and allows a fresh bounded lookup. A result found by that lookup can become the current match if it passes validation and has no explicit rejection. Last.fm supports optional `url` references. Historical Google `rym-url` / `metacritic-url` references retain their existing namespace; they are not removed or reassigned to another provider.

Plugins return candidates in `mediaPatch`, not instructions to overwrite user-curated identity. Parent enrichment must preserve canonical titles/artists, manual overrides and imported Added dates. Tags retain `source`, `rawName` and source IDs when supplied. MusicBrainz genres and general tags remain distinct; Discogs styles remain `style`; Last.fm freeform tags remain `general`, not automatically genres. The tag-normalization workstream controls canonical merging.

Shared browse keys: `popularityLastFm`, `scrobbles`, `ratingDiscogsValue`, `ratingDiscogsVotes`, `popularityDiscogs`, `ratingRymValue`, `ratingRymVotes`, `ratingMetacriticValue`, `ratingMetacriticVotes`. Last.fm global plays use `plugin.lastfm.playcount`. Zero values are retained. Track durations are seconds; native ordering is retained, while richer native positions stay in raw snapshots.

Once Spotify supplies a complete album track list, subsequent provider results preserve that edition's library tracks. Another provider can supply the library track list until Spotify supplies one. Each provider's own track list remains available in its snapshots and details.

Discogs refreshed rating/popularity covers **one release only**, not the old top-ten weighted rating or all-version popularity sum. `plugin.discogs.ratingScope` records which release. Historic aggregate snapshots are not rewritten by the plugin. Raw master and main-release bodies are both retained. This intentionally avoids the old fanout and makes the changed scope inspectable.

Google snapshots, current state, imported ratings, links and tag provenance remain available as historical data. The legacy importer still translates `rymGoogle` and `metacriticGoogle` under `google-custom-search`; retiring scraping does not rewrite those records. See [Google retirement and preservation](google-search-retirement.md).

## Serply (Rate Your Music)

`serply` retrieves indexed Google results through `GET https://api.serply.io/v1/search/`. Configure its `apiKey` in Providers → Serply → Settings; `SERPLY_API_KEY` is an optional environment fallback. It appears in the existing album metadata job and refresh workflows. Requests use the persistent gate, up to two concurrent requests, 250 ms between starts and optional configurable budgets. No request fetches RYM directly.

Search requests use mobile results with `gl=us`, `hl=en` and `num=10`, without overriding duplicate filtering. Device and language settings can change the returned evidence; the same identity and rating checks apply to every result.

Serply uses a 120-second request timeout. Account for gate waits and processing time as well as HTTP time within the job lease.

The gate settings are application limits, not account entitlements. Provider budgets and HTTP 429 cooldowns still apply. See [Serply authentication](https://www.serply.io/docs/guides/authentication).

The adapter permits at most five distinct searches normally. Only when removing a recognized OST/DJ Mix role suffix changes the cleaned search title (`queryTitle !== cleanTitle`) does the ceiling increase to six, with an additional simplified natural-language query. The original four full-title, release-path, quoted artist/title and natural-language queries remain intact. An owned, matched or legacy-hint release URL inserts a prioritized `site:<release-url>` query within the applicable ceiling. These are maximums, not required call counts: duplicate/exhausted queries and a selected release with both a rating and explicit description genres stop the loop early. HTTP/service failures propagate rather than triggering fallback searches. Matching guards, two-request concurrency and 250 ms start spacing remain unchanged.

Serply-owned references constrain candidates to the normalized release URL family; invalid owned references fail before searching. Only an explicit `rym-url` override marked `metadata.manualOverride: true` is authoritative over conflicting library identity/year metadata. Its exact URL-family constraint remains enforced, and provenance records the manual reference, source year and identity/year conflicts. The manual URL supplies identity evidence, not a rating: usable indexed fields are still required. Ordinary saved references do not gain this conflict bypass. Explicit edition headers such as `(Album; Label)` remain excluded except for identity and tags on a direct primary-issue `.p` page whose artist, title, kind and explicit release date all corroborate the library entry. Edition ratings and individual-review scores remain excluded even for manual overrides.

Historical Google RYM URLs are search hints, not constraints on new matching evidence. For Serply albums without any existing `rym-url` (including overrides), the helper reads at most eight media-scoped links from `google-custom-search` or `legacy-browser`, validates/deduplicates them and normalizes review/list child paths. Returned hints remain non-primary, foreign-owned and context-only (`searchHint: true`); the helper performs no database writes or ownership promotion. Invalid hints are ignored.

Without an explicit manual override, identity checks corroborate artist/title paths with indexed titles and descriptions. Normalization folds accents, the `æ`/`ae` and `ø`/`o` spellings used in RYM paths, apostrophes within words, `&`/`and`, and complete comma/underscore thousands groups; it does not concatenate arbitrary numbers or change date tokens. Displayed `w/` abbreviations require corroborating display/path evidence. Numeric artist or release suffixes require matching title/artist evidence and remain distinct stored identities. Contradictory identities are rejected.

Bounded identity exceptions require an exact indexed release date and corroborating release-kind/path evidence. Root-release bilingual matching uses explicit non-Latin names with bracketed Latin equivalents in the same result, consistent title/description evidence and native-script slugs. Supported anchored headers include `<title> by <artist> - RYM` and `By <native artist> - <Latin title> - Rate Your Music`. A Latin-only title must match the complete explicit native `[Latin]` pair in that result's description; the artist remains native or fully bilingual. There is no alias guessing, cross-result translation or relaxed date matching. Combined/featured credits and DJ Mix title composition have separate corroborated rules. Recognized soundtrack-role suffixes require explicit Soundtrack or Film Score evidence (or soundtrack-chart evidence), not merely classical music. Edition and role-label exclusions remain unchanged.

Review URLs are not automatically classified as albums. Their release kind comes from a matching owned release reference or corroborated title/description identity; unresolved reviews retain their review identity rather than inventing an album URL. Conflicting kinds and song/music-video reviews are rejected. Singles require an owned single reference. Review/list pages can supply explicit aggregate rating/count pairs, never structured personal-review ratings.

Only recognized trailing edition labels are removed for lookup: deluxe (including `Deluxe Version`), expanded, anniversary, special/collector's edition and remaster forms. Supported compounds include ordinal anniversary analogue-remaster editions and ordinal `Anniversary Edition` labels followed by `/ Remastered YYYY` or `; YYYY Remaster`. The adapter preserves arbitrary slash lists, live/remix labels and meaningful parentheticals. Trailing brackets are checked before the final dash suffix, preserving interior dashes and date ranges; stripping never produces an empty title. The first query retains the full input title. An earlier original-release year is allowed for a cleaned edition title only when both path and indexed title corroborate it. Other explicit year conflicts remain rejected unless an explicit manual override applies.

To use an underlying album rather than a streaming edition, review the release identity. For exceptions beyond the automatic edition rules, use an explicit observed RYM reference supported by release-group, edition-list or tracklist evidence. Preserve the library's title, artist, release date and tracklist, and retain the source URL and edition differences in provenance and the override audit note. Different track segmentation or an abridged compilation can qualify when the underlying work is established; unrelated DJ mixes, remixes, live recordings and similarly named compilations must not be substituted. Do not invent URLs, copy legacy scores or weaken identity checks.

Release results are preferred over review/list headers, with non-`.p` results preferred within the same page class; ratings and genres are selected only within the same normalized release identity. Terminal `.p` is removed for identity comparison, not from the observed source URL/reference. URL-restricted fallback queries preserve an observed `.p` URL from the owned reference, selected result or legacy hint rather than silently querying its stripped counterpart. Rating provenance distinguishes `primary-issue` from `release`. This is request/identity handling, not proof of equivalent rating scope or improved coverage; see the [research caveat](serply-search-notes.md#rym-p-suffix).

Structured `metadata.rating` and `metadata.reviews` are supported on release results. Explicit aggregate snippet pairs preserve more precision when available. Scores without a count clear the old count instead of combining observations. The adapter extracts genres and descriptors from explicitly labelled fields on results for the selected release. It does not infer tags from review prose or infer mood from audio. In flattened genre lists, ambiguous joins and truncated tokens are skipped unless corroborating evidence establishes the labels. Each extracted tag retains its field kind and evidence URL in normalized snapshot provenance. Indexed observations can differ between pages and are not labelled current RYM values.

Provenance distinguishes `rated`, `genres-only` and `identity-only` matches, with identity/year evidence, source URLs and retrieval time. An identity-only match saves its link/reference without inventing a rating or genres; it is not a rated success. No matching identity throws `ProviderItemNotFoundError`. Full search responses remain in provider history, and diagnostics distinguish empty results, rejected candidates and missing fields.

Album serialization prioritizes the validated `ratingSourceUrl` when metadata has a finite RYM score in range and Serply provenance with `matchStatus: rated`. The link points to the exact page that supplied the rating, including valid review/list child URLs, not the identity or genre source; child URLs are validated through their release parent without rewriting the displayed destination. The serializer reorders or supplies this response link without database writes, new queries or provider calls. Missing/invalid rated provenance and genres-only/identity-only results retain the existing generic/legacy link fallback. This link fix does not acquire or validate a new rating.

Bing is not a production fallback. See the [search notes](serply-search-notes.md) for query handling and evidence limits.

### Replaying saved tags

Run `pnpm --filter @repo/server exec tsx scripts/replay-rym-tags.ts --report=/private/path/preview.json`. The default is read-only and local; remote use requires an explicit direct connection in `RYM_REPLAY_DATABASE_URL`. Review the database target, skipped albums, proposed memberships and evidence URLs. Apply with the same command plus `--apply --review=<preview hash>` and a new report path. Take a recovery point first and repeat the preview after commit; it should propose zero additions. Reports contain library data and should stay private.

Replay considers successful saved Serply results for the current release identity, including earlier confirmed snapshots of the same issue. Retained structured Google genre names can disambiguate flattened words; they do not link a Google search result to an album. The replay inserts only missing album tags, memberships and source occurrences after resolving existing tag identities. ## Current Service Constraints

MusicBrainz requires an identifying User-Agent and at most one request per second. The plugin uses configured app name/version/contact and the JSON release-group API, including artists, tags, genres and URL relations in the same lookup. Public reads need no account authentication. [Official API documentation](https://musicbrainz.org/doc/MusicBrainz_API), [search reference](https://musicbrainz.org/doc/MusicBrainz_API/Search).

Last.fm documents `album.getInfo` by artist/album or MBID, optional username-scoped plays, seconds for track duration, and error 29 for rate limiting. The key is required; username is optional and missing personal counts are not zeroed. [Official album.getInfo documentation](https://www.last.fm/api/show/album.getInfo).

A user token is required by this adapter, including searches. Conservative legacy spacing remains unchanged; no claim of current account entitlement or full live schema verification is made. [Official developer portal](https://www.discogs.com/developers), [official client quickstart](https://github.com/discogs/discogs_client/blob/master/docs/quickstart.md), [official model definitions](https://github.com/discogs/discogs_client/blob/master/discogs_client/models.py).

Google scraping is unconditionally retired in this application, independent of account eligibility or service retirement dates. No Google credential fields or environment fallbacks are exposed. Existing environment files and encrypted secret rows remain untouched. New Google jobs are rejected, and existing queued jobs fail as unsupported when claimed without HTTP. See [retirement behavior and offline tests](google-search-retirement.md).

## Additional Stored Album Details

In album **Sources**, open a provider's history for its retained snapshots and jobs. MusicBrainz, Discogs and Last.fm also offer a collapsed **More album info** section using the latest stored results. Opening album details or history uses stored data. Edit a provider ID on its Sources row and choose **Save and refresh**, or use the row's Refresh or **Refresh all** in the Sources summary line, to queue new work.

MusicBrainz contributes release types, disambiguation, artist countries, weighted original tags and existing URL relationships. Discogs contributes edition-specific labels/catalogue numbers, formats, companies, credits, notes, native track positions and have/want counts. These counts describe the fetched release, not every edition. Last.fm contributes wiki text/publication date, source track links and original tags. Provider prose is rendered as text, never executable HTML.

Future explicit scrapes retain these details from responses already needed by the adapters; no extra provider calls are added. Provider-specific browse fields are populated on those future scrapes. Existing albums can show retained detail immediately without being scraped again. Malformed or absent stored payloads omit that source's optional details.

## Offline Verification

### Last.fm Response Audit

An automatic Last.fm name lookup can require review when a complete Spotify album tracklist confirms a longer library album. A response with three or four tracks, at most half as many as the library, needs at least three known durations, at most half shared track titles, and no possible duration alignment within ten seconds to trigger review. This keeps the response in job diagnostics without installing it or counting it toward a provider stop. Existing Last.fm URLs and MBIDs continue to take precedence. Single-track continuous mixes and responses without enough track evidence follow the regular lookup.

An album job with `options: { "includeTopTags": true }` requests [album.getTopTags](https://www.last.fm/api/show/album.getTopTags) after a successful `album.getInfo`. It uses the resolved album identity and the same provider request gate. No other job gains an extra request. The snapshot preserves the original album and the dedicated response separately. Last.fm's count is a relative weight out of 100, not a vote count. The adapter retains all returned rows in the raw response but only adds dedicated tags with weight at least 10 to the usual album tag merge. Ordinary album tags are retained even if absent from the dedicated list.

For tag enrichment without replacing tracks, artwork, links or other canonical fields, set both `includeTopTags: true` and `tagsOnly: true`. Use one explicit album per job.

Use the artist and album names returned by `album.getInfo` for `album.getTopTags`, even when the first lookup used an MBID. Ranked tags are freeform labels, not necessarily genres.

Tags support arrays, a single named object, an empty outer string and an empty outer object. Tracks support arrays and a single named object; null or missing duration stays unknown, while numeric zero remains zero. Empty image text is valid missing artwork, not an invalid URL exception. Last.fm album URLs may include the `+noredirect` path segment. Corrected references use the same URL validation and decode the actual artist/album segments. Malformed URLs, missing identifiers, invalid counts and malformed collection entries still fail validation; no catch-all empty-data fallback is used.

Run the repeatable offline audit from the server workspace:

```sh
pnpm exec tsx scripts/audit-lastfm-responses.ts
```

It uses a read-only repeatable-read transaction, scans snapshots in batches of 100, supplies stored responses through a mocked request function, blocks global fetch and exits nonzero on any failure. It does not import data, queue jobs, retry failures or print credentials/raw payloads. Legacy unwrapped album bodies are wrapped only for offline adapter replay.

`lastfm-response-matrix.test.ts` checks accepted and rejected response shapes offline. `integration/lastfm-jobs.integration.ts` checks the adapter, gate, queue and persistence using mocked HTTP and a temporary database.
